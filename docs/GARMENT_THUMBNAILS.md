# 의류 카드 썸네일 — 2026-11-11

옷장과 추천의 작은 의류 카드에 최대 384×384px WebP(품질 82)를 사용합니다.
가로세로 비율·누끼 투명도를 보존하고 작은 이미지를 확대하지 않습니다.
원본 JPEG와 기존 누끼 PNG를 덮어쓰지 않으며, 상세/확인 화면과 GPU 착샷 입력은
기존 크기 이미지를 계속 사용합니다. 전신 사진·착샷 결과 보관 정책에는 변경이 없습니다.

## API와 프론트 연결

- 백엔드: `GET /api/v1/garments/{id}/image?kind=thumbnail`.
- 프론트 인증 프록시: `GET /garment-images/{id}?size=thumbnail`.
- 기존 `kind=original`, `kind=cutout`, `/media/...`, 크기 없는 프론트 이미지 주소는 유지합니다.
- `garment_art(g, thumbnail=true)`로 작은 카드에서만 사용합니다. 기존 lazy loading은 유지하고
  `decoding="async"`를 추가했습니다.
- 로그인하지 않으면 401, 다른 사용자의 의류는 404입니다. 파일 캐시가 있어도 먼저 DB 소유권을
  검사하며 파생 파일 경로를 임의 `/media/...` 요청으로 열 수 없습니다.
- 공개·로컬 이미지 응답 모두 `private, no-store`를 사용합니다. 계정 전환/로그아웃 뒤
  브라우저가 인증 없이 이전 사용자 이미지를 재사용하도록 캐시 정책을 완화하지 않았습니다.

## 생성·갱신·정리

썸네일은 원래 의류 폴더 안의 `thumb-v1-384-{source-path-hash}.webp`에 저장합니다.
DB 컬럼 변경이나 마이그레이션은 필요 없습니다.

1. 신규 업로드·재분석에서 분석 결과를 적용한 뒤 준비합니다. 누끼가 있으면 누끼,
   없으면 원본에서 생성합니다. 원본 이미지의 경로는 불변이며 재분석은 새로운 누끼 파일 경로를
   발행하므로 새 누끼에는 새 썸네일 키가 적용됩니다.
2. 기존 의류는 최초 조회 시 생성하고 이후 저장된 파일을 재사용합니다. 이름·색상 등
   속성만 바뀌면 이미지가 같으므로 다시 인코딩하지 않습니다.
3. 캐시가 없을 때 사용자→의류 순서로 PostgreSQL 행 잠금을 얻고 최신 상태를 다시 확인합니다.
   두 백엔드의 중복 생성, 재분석, 의류 삭제·탈퇴와 충돌해 폴더를 다시 만드는 상황을 막습니다.
4. 썸네일 저장 실패 시 기존 이미지를 표시합니다. 의류 등록·원본 보존은 유지하고 다음 요청에서
   다시 생성할 수 있습니다. 원본까지 없으면 404입니다.
5. 재분석의 DB 커밋이 실패하면 기존 DB가 가리키는 이미지와 썸네일을 계속 사용합니다.
   사용하지 않는 파생 버전은 의류 삭제·탈퇴의 폴더 정리에 함께 포함됩니다.
6. 삭제는 기존대로 DB 확정 후 폴더 정리합니다. 커밋 실패 시 원본·썸네일 보존,
   파일 정리 실패 시 접근 차단 후 DB 정리 작업으로 재시도합니다.

기존 시연 데이터의 사전 생성은 다음 명령으로 수행합니다. `.env` 접근을 감사 훅으로 차단하고,
명시적인 기존 시연 DB/스키마/저장소를 사용합니다. 계정 생성·seed·DB 행 수정은 하지 않습니다.

```powershell
conda activate univ18
$env:FITJANG_SKIP_DOTENV = "1"
python -m scripts.garment_thumbnails
```

다른 저장소는 `--database-url`, `--schema`, `--storage`를 명시합니다.
DB 행이 가리키는 원본·누끼 파일을 서버 외부에서 같은 경로에 덮어쓰는 작업은 지원하지 않습니다.
이미지 교체는 등록/재분석 API로 수행해야 버전이 갱신됩니다.

## 검증

집중 테스트는 실제 PostgreSQL에서 15개 통과했습니다. 다음을 포함합니다.

- WebP 크기·투명도·메타데이터 제거·작은 이미지 확대 방지·원본 불변.
- 신규 업로드 사전 생성, 기존 누끼 최초 생성, 두 번째 조회에서 인코딩 없이 재사용.
- 캐시가 있는 다른 사용자/비로그인 요청 차단, 임의 저장 경로 비공개.
- 재분석 후 새 이미지 선택과 DB 커밋 실패 시 이전 이미지 유지.
- 썸네일 쓰기 실패 시 등록 성공·기존 이미지 대체 및 장애 해소 후 재생성.
- 의류 삭제/탈퇴 정리, DB 삭제 커밋 실패 보존, 파일 정리 실패 재시도.
- 실제 HTTP 동시 조회 및 생성 중 삭제/탈퇴의 PostgreSQL 잠금 동작.
- 로컬/멘토 프론트 카드의 썸네일 연결, 상세 화면의 기존 이미지 유지.

전체 회귀 테스트는 실제 PostgreSQL 모드에서 **472개 통과, 2개 건너뜀**(232.89초)입니다.
건너뛴 것은 별도 D checkout과 별도 실사 이미지 입력이 필요한 선택적 테스트입니다.
변경 파일 Ruff와 `git diff --check`도 통과했습니다.

## 로컬·멘토 적용 및 공개 HTTPS 비교

기존 42벌의 썸네일 사전 생성은 `ready=42, fallback=0, skipped_unavailable=0`으로 완료했습니다.
로컬 3000/8002와 멘토 3001/8003을 재시작했고 자동 실행 감독 상태는 ready입니다.
GPU 프로세스는 재시작하지 않았으며 동일 PID 23488, health=ok를 확인했습니다.

기존 계정 6개·프로필 6개·의류 42개·속성 42개·추천 70개·코디 109개·피드백 7개·
저장 착샷 2개의 레코드 해시, 기존 파일 65개와 자격증명 파일 4개의 해시가 보존됐습니다.
썸네일 42개만 추가돼 저장 파일은 총 107개입니다. `.env`는 읽거나 수정하지 않았습니다.

측정 대상은 기존 QA 계정의 동일한 의류 9장입니다. 공개 DNS의 Funnel 릴레이 IP
`103.84.155.217`에 원래 호스트명으로 TLS를 검증하며 접속했습니다.
동시 HTTP 요청 최대 4개, 브라우저 캐시 없는 클라이언트에서 전체 이미지 다운로드 시간을 측정했습니다.
HTML과 로그인 시간은 아래 이미지 시간에 포함하지 않았습니다.

| 구분 | 총 바이트 | 3회 이미지 다운로드 시간 | 중앙값 |
|---|---:|---|---:|
| 기존 크기 이미지 | 8,485,307 | 30.973 / 48.630 / 48.187초 | 48.187초 |
| 384px WebP 썸네일 | 181,786 | 5.402 / 3.479 / 7.741초 | 5.402초 |

전송량 **97.9% 감소**, 같은 측정 구간의 중앙값 기준 다운로드 시간 **88.8% 감소**입니다.
적용 전 별도 단회 측정은 18.312초였습니다. 공개 경로의 변동이 커서 이 단회와의 단순 비교 대신,
적용 후에도 유지한 기존 크기 엔드포인트와 새 썸네일 엔드포인트를 번갈아 세 번씩 측정했습니다.
서버 PC에서 공개 릴레이를 경유한 검증이며 실제 노트북 회선을 재현한 테스트는 아닙니다.
절대 로딩 시간이 모든 사용자에게 5.4초로 고정된다는 의미가 아닙니다.

- 기존 크기 응답의 SHA-256은 적용 전과 일치했습니다.
- 공개 옷장 HTML의 이미지 9개가 썸네일 주소를 사용하며 응답은 image/webp, private/no-store입니다.
- 공개 HTTPS에서 비로그인 401, 다른 실제 계정 404를 확인했습니다.
- 실제 브라우저에서 로컬·공개 옷장 9장 모두 로드 완료·384×384를 확인했습니다.
  상세 화면은 기존 1254×1254 이미지를 사용하며 공개 화면 콘솔 오류·경고는 없었습니다.
