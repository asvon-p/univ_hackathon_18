# 저장한 스타일을 내 옷으로 재현

2026-11-12 · 계약 2.3 · DB 0018

## 구현 범위와 사용 방법

확장 계획서의 **속성 비교 기준선**을 구현했다. 코디 추천 → 사진 올리고 특징 확인하기 →
JPG·PNG·HEIC 업로드 → 상의·하의·아우터 영역 지정·분석 → 특징 확인 → 내 옷으로 추천 순서다.
기존 필수 의류·일정 선택은 사진 관리 화면을 오갈 때 유지한다.

얼굴·배경을 빼고 한 벌의 영역을 드래그하거나 비율로 입력한다. 기존 CLIP/rembg 엔진이
해당 영역의 색상·패턴·종류·스타일을 추정하고, 사용자가 수정·확인한 특징만 추천에 사용한다.
보이지 않는 종류는 생략할 수 있다. 분석 실패·시간 초과·demo 분류기에서는 픽셀 색상만
추정하고 나머지를 수동 입력하게 한다. 사진 속 옷은 옷장에 소유 의류로 자동 등록하지 않는다.

**아직 포함하지 않은 기능:** 사진 전체 임베딩/FashionCLIP 검색, 자동 인물·의류 영역 탐지,
핏·실루엣·소재·치수 판단, SNS 로그인·URL 수집. 기존 CLIP 속성 분류를 검색 임베딩으로
설명하지 않는다. 자동 추정은 정답이 아니므로 사용자 확인이 필요하다.

## 추천과 GPT의 역할

서버가 소유권·사용 가능 상태·슬롯·필수 ID·제외 의류·일정의 명시적 복장 조건을 검증한다.
최대 3개 조합을 반환하고 필수 의류는 대체 추천에서도 유지한다. 일정의 시간·목적·실내외·
구간 기온·아우터 소지 계획은 기존 일정 엔진을 재사용한다. 충돌한 조건은 임의로 없애지 않는다.

| 입력 | 색 조화 C | 상황 O | 선호 P | 일정 S | 참고 R |
|---|---:|---:|---:|---:|---:|
| 참고 사진 | 15 | 20 | 15 | 0 | 50 |
| 참고 사진 + 일정 | 15 | 0 | 15 | 35 | 35 |

선호가 없으면 P를 제외해 정규화한다. R은 알려진 특징만 비교하며 색상 계열 일치에는
부분 점수, 완전 일치에는 전체 점수를 준다. 미정 속성을 일치로 취급하지 않는다.
색상 중심/스타일 중심/균형을 선택할 수 있다. 점수는 재현 확률이나 검증된 정확도가 아니다.
결과에 닮은 점·다른 점, 필수 의류 때문에 생긴 차이와 지원하지 않는 판단을 표시한다.

GPT6-Luna는 서버가 만든 후보의 순서·설명만 판단한다. 이미지·사용자/의류/일정/사진 ID·
파일 경로를 전송하지 않고 확인된 특징과 익명 후보 비교만 전달한다. `store=false`를 유지한다.
실패·타임아웃·잘못된 출력은 검증된 로컬 추천으로 대체한다.

최초 구현에서는 로컬·멘토 실행기를 `local`로 유지하고 모의 HTTP로 판단 계약을 검증했다.
후속 실행기는 `.env` 외부에 등록한 키가 있으면 GPT6-Luna 판단을 선택하고 실패 시 local로 대체한다.
설정·실제 연결 범위는 [GPT 판단 연결](REQUIRED_GARMENTS.md#GPT-판단을-로컬멘토-시연에-연결하기-2026-11-12-후속)을 참고한다.

## API 계약

모든 경로는 `/api/v1` 아래이며 JWT가 필요하다. 타인 또는 없는 ID는 404다.

| 메서드 | 경로 | 용도 |
|---|---|---|
| POST | `/style-references` | multipart `file`, draft 생성(201) |
| GET | `/style-references` | 본인 목록, limit/offset |
| GET | `/style-references/{id}` | 버전·상태·특징·영역·focus |
| GET | `/style-references/{id}/image` | 본인 이미지, `private, no-store` |
| POST | `/style-references/{id}/analyze` | 단일 의류 영역 분석 |
| PATCH | `/style-references/{id}` | 특징 확인 후 ready, 버전 증가 |
| DELETE | `/style-references/{id}?expected_version=N` | 사진·특징 삭제, 204 |

분석 입력 예:

```json
{
  "expected_version": 1,
  "region": {"category": "top", "x": 0.29, "y": 0.18, "width": 0.42, "height": 0.29}
}
```

좌표는 정상화 이미지의 0~1 비율이고 이미지 안에 있어야 한다. 각 변 최소 32픽셀.
확인 입력 예:

```json
{
  "expected_version": 2,
  "focus": "balanced",
  "features": [{"category": "top", "color": "gray", "pattern": "solid", "subcategory": "t-shirt", "style_candidates": ["casual", "minimal"]}]
}
```

카테고리 중복·전부 미정인 특징·클라이언트의 추출 출처 위조는 거절한다.
추천 요청에는 `reference_id`와 `reference_version`을 함께 추가한다. 기존
`required_garment_ids`, `schedule_id`, `schedule_version`, `outerwear_policy`와 병용한다.
`style_reference` 내용은 직접 주입할 수 없고 서버가 DB에서 본인 사진을 읽는다.

버전 변경은 `409 REFERENCE_CHANGED`, 미확인은 `422 REFERENCE_NOT_CONFIRMED`다.
분석·수정·추천 저장 중 버전도 다시 검사한다. 결과는 `reference_matches`, `wearing_plan`,
`limitations`, `score_components`, `policy_version`을 포함한다. 과거 추천은 당시 특징을 보관한다.

## 보관·삭제·처리량

- 기존 정상화(JPEG 변환·회전·EXIF 제거)를 재사용한다. 최대 10MB, 본인 전용 저장 경로다.
- 2026-11-12 정책: 원본은 일회성이다. 업로드 후 영역 선택용으로 최대 30분만 보관한다.
  `analyze`는 `regions` 1~3개를 한 번에 받는다(기존 `region` 한 개도 호환).
  검증된 영역을 메모리로 읽은 뒤 원본 참조 해제와 삭제 작업을 커밋하고, 원본 삭제 후 분석한다.
  분석 성공·실패·타임아웃 후 원본으로 재분석할 수 없으며 새 업로드 또는 수동 키워드 수정이 필요하다.
  분석 없이 키워드를 확인하는 PATCH도 원본을 제거한다. 잘못된 입력은 원본을 소비하지 않는다.
- 미완료 업로드는 DB 만료 시각으로 접근을 즉시 차단하고 시작 시/주기적 정리 작업에서 삭제한다.
  서버가 꺼져 있는 동안에는 물리 삭제할 수 없으며 재시작 시 정리한다. 정상 시연 서버 정리 간격은 30초다.
  분석 crop은 전용 임시 디렉터리에서 작업 종료 시 삭제하고, 비정상 종료 잔여물도 30분 후 정리한다.
- 색상·패턴·종류·스타일 키워드는 본인이 삭제하거나 탈퇴할 때까지 보관한다.
  원본·영역 좌표·이미지 미리보기·얼굴 특징은 장기 보관하지 않는다. API의 `image_url`은 nullable이며,
  `image_available`, `image_expires_at`, `retention_policy=keywords_only`를 제공한다.
  원본이 없으면 화면은 키워드 카드와 수정 폼만 표시한다. 키워드는 기존 추천 조건으로 재사용한다.
- 마이그레이션 0019는 기존 참고 사진을 만료 대상으로 지정한다. 실제 삭제는 DB 커밋 후 작업자가 한다.
  기존 참고 ID·버전·키워드·상태·추천 문맥, 계정·옷장·전신 사진·착샷은 유지한다.
- 사용자별 50개(파일 정리 대기 포함), 분석 분당 10회, 프로세스별 분석 접수 2개다.
  두 API 프로세스에서는 최대 4개 접수이며 GPU 착샷 대기열과 별도다.
- 사용자 요청 제한은 429/Retry-After, 모델 접수가 가득 차거나 영역당 최대 20초를 초과하면
  픽셀 색상 기준선과 수동 키워드 확인으로 전환한다.
  타임아웃 뒤 실제 스레드가 끝날 때까지 접수 슬롯을 유지한다.
- 업로드 파일 쓰기 전에 DB 정리 작업을 남긴다. 저장 실패 시 파일을 정리한다.
- 삭제는 DB 커밋 후 파일을 지운다. 파일 삭제 실패는 DB 작업으로 남겨 재시도한다.
  DB 커밋 실패로 살아 있는 사진이 사라지지 않는다.
- 사진 삭제 시 과거 추천의 관련 특징·설명·혼합 점수를 정리한다. 옷장·일정은 보존한다.
  일정만 삭제하면 참고 비교는 유지한다. 탈퇴 시 FK와 사용자 저장 폴더 정리로 삭제한다.
- 소스 접근 차단, 비공개 이미지, 기존 계정·데이터·GPU 착샷 설정을 유지한다.

## 검증 기록

2026-11-13 일회성 원본·키워드 보관 변경 검증:

- 실제 PostgreSQL 임시 스키마 기반 API·마이그레이션·HTTP E2E와 관련 어댑터/단위 회귀 151개 통과.
- 원본 삭제 후 키워드 유지, DB 커밋 실패 시 원본 보존, 파일 삭제 실패 시 접근 차단·재시도,
  만료 전후 접근 차단, 다른 사용자 접근 차단, 같은 원본 동시 분석 200/409를 검증했다.
- 기존 ID·버전·키워드·상태를 보존하는 0018→0019 마이그레이션과 분석 임시 파일의
  정상 종료·비정상 종료 후 정리를 검증했다.
- 로컬·멘토 서버에 0019 적용. 합성 인물의 상의·하의 영역을 실제 화면에서 일괄 분석하고,
  원본 없이 키워드를 확인·저장한 후 필수 의류·일정을 유지한 GPT 추천을 확인했다.
- 공개 HTTPS에서 동일 계정의 키워드 목록과 사진 없는 화면을 확인했다. 파일 선택 자동화 도구가
  멈춰 업로드는 실제 HTTP로 검증하고, 영역 선택·분석·확인은 브라우저에서 수행했다.
- 운영 정리 작업 검증에서는 새 검증 사진만 만료시켜 즉시 이미지 조회 404, 약 7초 후 파일 삭제를 확인했다.
  기존 SNS 참고 사진은 배포 전 0개였으며, 기존 계정·옷장·추천·전신 사진·착샷 데이터는 변경하지 않았다.

아래 항목은 일회성 보관 정책 도입 이전의 검증 이력이다.

기존 서비스와 분리된 실제 PostgreSQL 임시 스키마에서 `FITJANG_SKIP_DOTENV=1`, 명시적
테스트 DB·JWT, `.env` 열기 차단으로 실행했다. 결과물은 Git 제외 `.demo` 안에 둔다.

- 통합 회귀 243개 통과: API·마이그레이션·추천·일정·필수 의류·피드백·공개 경계.
- 실제 HTTP 동시 요청: 사용자별 사진·옷장·일정·추천 격리, 같은 버전 수정 경쟁 200/409.
- 실제 브라우저와 로컬 CLIP: 합성 인물 사진 업로드 → 상의·하의 영역 분석 → 특징 확인 → 추천.
  회색 무지 티셔츠·베이지 바지가 추출되고 회색 상의 조합이 빨간 상의보다 앞섰다.
  필수 아우터, 실내 소지/실외 착용 안내가 유지됐다. 사용자 실제 사진은 사용하지 않았다.
- 모델 실패·타임아웃·잘못된 응답의 대체, 파일 삭제 재시도·커밋 실패·탈퇴 정리·분석 제한 검증.
- 최종 변경 후 관련 PostgreSQL/어댑터/실제 HTTP 테스트 34개 재검증 통과.
- 로컬 8002/멘토 8003에 계약 2.3·DB 0018 적용. 공개 HTTPS에서도 사진 특징·필수 아우터·
  실내외 일정이 함께 반영된 추천 화면을 확인했다. 임시 검증 계정은 종료 후 정리했다.
  기존 주요 9개 테이블의 전체 행 해시와 저장 파일 목록·크기·수정 시각은 적용 전후 동일했다.
- 합성 사례는 흐름 검증이며 다양한 SNS 사진의 재현 정확도나 사업적 효과를 입증하지 않는다.
  실제 대학생 평가와 임베딩 추가 비교는 후속 작업이다.
