# 이미지 전송·GPU 수용량 점검 — 2026-11-11

현재 RTX 5090을 사용자별로 나누어 할당하는 기능은 없습니다. 하나의 GPU 작업자가
옷 한 벌 단위의 작업을 순서대로 처리합니다. 여러 사용자의 접속은 가능하지만
동시에 여러 착샷을 GPU에서 계산하는 구조는 아닙니다.

이 문서는 초대 코드 제거 시점의 성능 기준선입니다. 이후 2026-11-11 의류 썸네일을
적용했습니다. 구현·검증·속도 비교는 [GARMENT_THUMBNAILS.md](GARMENT_THUMBNAILS.md)를 참고하세요.
GPU 병렬화는 적용하지 않았습니다.
이후 전역 접수 상한·사용자당 1개 제한·순환 대기열도 적용했습니다.
최신 처리 정책과 실제 3명 동시 GPU 검증 결과는 [TRYON_QUEUE.md](TRYON_QUEUE.md)를 참고하세요.
기존 계정·의류·이미지·착샷 데이터를 유지하며 `.env`는 읽거나 수정하지 않았습니다.

## 1. 초대 코드 제거 범위

- 로컬·공개 회원가입 입력란, 프론트 Form/연결 함수, 백엔드 요청 스키마·검사·오류 코드 제거.
- 실행기와 `.env.example`의 관련 설정, 신규 시연 자격증명 생성 로직 제거.
- API는 `{email, password, nickname?}`를 받습니다. 기존 클라이언트는 `invite_code`를
  보내지 않아야 합니다. 제거된 필드를 보내면 기존의 추가 필드 금지 정책에 따라 422입니다.
- 과거 `SIGNUP_INVITE_CODE` 프로세스 환경변수가 남아도 가입을 제한하지 않습니다.
  `.env`나 기존 자격증명 파일을 수정할 필요가 없습니다. 기존 파일에 남은 값은 사용하지 않습니다.
- 학습 프로세스의 환경변수 제거 목록에는 과거 비밀값 전달을 막기 위해 이름만 남겼습니다.
- 중복 이메일 409, 비밀번호 검증, JWT, 사용자별 접근 제한, 공개 요청 제한·경로 보호는 유지합니다.
  새 가입자의 사진은 기존대로 session 보관 정책입니다. DB 마이그레이션은 필요 없습니다.

## 2. 이미지 지연: 같은 자료로 비교한 측정

사용자 설명상 데스크톱·노트북은 계정·주소·네트워크가 모두 달랐습니다.
따라서 원래 두 접속의 차이를 노트북 성능 탓으로 확정할 수 없습니다.
아래에서는 기존 QA 계정의 동일한 옷 9장을 사용했습니다.

| 경로 | 옷장 HTML | 이미지 9장 전체 | 이미지 전송량 | 이미지 Cache-Control |
|---|---:|---:|---:|---|
| 로컬 `127.0.0.1:3000` | 0.018초 | 0.336초 | 8,485,307바이트 | private, max-age=300 |
| 멘토 서버 직접 `127.0.0.1:3001` | 0.018초 | 0.270초 | 동일 | private, no-store |
| 공개 HTTPS Funnel `:8443` | 1.111초 | 19.266초 | 동일 | private, no-store |

방법: 기존 서버에서 읽기 전용 HTTP 요청, 이미지 동시 요청 최대 4개, 캐시 없는 클라이언트.
공개 DNS로 받은 Funnel 릴레이 IP에 연결하고 원래 호스트명으로 TLS를 검증했습니다.
같은 PC에서 외부 릴레이를 경유한 단회 측정이며 실제 노트북·외부 통신사 환경의 측정은 아닙니다.
배치 시간에는 클라이언트의 이미지 크기 확인과 메모리 내 축소 실험도 조금 포함됩니다.
개별 이미지 HTTP 시간은 축소 실험 전에 측정했습니다. 외부 이미지별 시간은 3.336~9.963초였습니다.

### 확인된 원인

1. **카드에도 큰 누끼 PNG를 전송합니다.** 브라우저는 `/garment-images/{id}`로 요청하고,
   프론트는 인증을 붙여 백엔드의 cutout을 우선 가져옵니다. 누끼가 없으면 원본으로 대체합니다.
   작은 카드 전용 썸네일·반응형 이미지 크기 선택은 없습니다.
   QA 이미지들은 1254×1254이며, 예를 들어 한 장은 1,587,652바이트입니다.
2. **공개 경로의 전송 비용이 큽니다.** 공개 Funnel은 릴레이와 데스크톱의 인터넷 업로드 경로를
   거칩니다. 로컬은 이 비용이 없습니다. Tailscale은 조정할 수 없는 대역폭 제한이 있음을
   [공식 문서](https://tailscale.com/docs/features/tailscale-funnel)에 명시합니다.
   이번 측정만으로 릴레이 제한·호스트 업로드·특정 네트워크 중 어느 하나의 비중을 확정하지는 않습니다.
3. **공개 서버는 이미지도 재사용 캐시를 금지합니다.** 보안 미들웨어가 모든 응답에
   `private, no-store`를 적용합니다. 로컬 이미지의 5분 캐시와 달리 재방문 시 다시 전송합니다.
   위 측정은 양쪽 모두 캐시 없이 비교했으므로 19초 차이는 캐시만으로 생긴 결과는 아닙니다.
4. 이미지마다 새 HTTP 클라이언트로 백엔드에 요청합니다. 연결 재사용 개선 여지는 있지만,
   이번 직접 접근이 0.3초 이내였으므로 측정된 큰 차이는 주로 공개 이미지 전송에서 발생했습니다.

`loading="lazy"`는 이미 구현되어 있습니다. 지연 로딩이 없어서 생긴 문제라고 볼 수 없습니다.
옷장 이미지 조회에는 GPU 추론이 들어가지 않습니다. GPU 분할은 이 지연의 직접 해결책이 아닙니다.
홈 페이지 자체가 느린 경우에는 날씨→옷장→프로필→추천의 순차 요청도 별도 확인 대상입니다.

### 저장된 이미지 크기와 개선 효과 추정

현재 의류 42개를 읽기 전용으로 조사했습니다. 원본 JPEG 합계는 약 8.14MB,
화면에 선택되는 누끼/원본 합계는 약 21.48MB입니다. 표시 이미지의 중앙값은 약 331KB,
최대는 약 1.74MB였습니다. 누끼 PNG는 투명 배경을 보존하지만 원본 JPEG보다 커질 수 있습니다.

QA 9장을 메모리에서만 최대 384px WebP 품질 82로 변환한 합계는 181,786바이트였습니다.
원래 8.49MB 대비 **약 97.9% 감소**입니다. 기존 파일은 수정하거나 덮어쓰지 않았습니다.
이는 용량 실험이며 실제 썸네일 API의 속도·시각 품질 검증을 마친 결과는 아닙니다.

권장 순서는 다음과 같습니다.

1. 옷장 카드용 256/384px 썸네일을 업로드·재분석 후 준비하고 원본은 착샷/상세 화면에 보존.
   매 조회마다 큰 이미지를 다시 변환하지 않도록 파생 파일을 관리합니다.
2. 의류 이미지에만 버전·ETag 기반 인증 재검증을 검토. 공개 공유 캐시는 금지하고,
   로그아웃·계정 전환·삭제 때 다른 사용자 사진을 재사용하지 않는지 확인해야 합니다.
   전신 사진·착샷의 `no-store` 정책을 함께 풀면 안 됩니다.
3. 백엔드 HTTP 연결 재사용, 홈 화면 독립 요청 병렬화. 이후 실제 노트북에서 다시 측정.

## 3. GPU 작업 흐름과 실제 제한

브라우저에서 착샷 시작 → 프론트가 사용자·전신 사진·옷 소유권 확인 → 결과 작업 생성 →
하의 작업 제출 → 완료 결과를 사람 사진으로 사용 → 상의 제출 → 필요하면 아우터 제출 →
계정의 사진 보관 정책에 따라 결과 처리 → 브라우저 표시 순서입니다.
각 단계는 개별 GPU 큐 항목입니다. 두세 벌을 한 번에 만드는 단일 GPU 작업이 아닙니다.

| 항목 | 현재 동작 | 의미 |
|---|---|---|
| GPU | RTX 5090, 약 31.8GiB VRAM | 한 장을 공유 |
| 실행 worker | 1개 | 실제 GPU 추론은 동시에 1단계 |
| 대기 큐 | FIFO, 최대 8개 | 실행 1개와 대기 8개가 공존 가능 |
| 가득 찬 큐 | GPU API HTTP 429 | 프론트에서는 일반 실패 안내, 자동 재시도 없음 |
| 사용자별 GPU 제한 | 없음 | 한 사용자의 다른 코디 요청들이 대기열을 채울 수 있음 |
| 동일 요청 재사용 | 같은 사용자·전신 사진 버전·코디 기준 | 다른 코디의 다중 요청까지 제한하지 않음 |
| 프론트 상태 보관 | 최근 40개 | 실행 제한이 아니며 활성 Task 수의 상한도 아님 |
| 상태 조회 | 약 2초 간격 | 계산 완료 후 화면 반영까지 추가 지연 가능 |
| 단계 제한 시간 | 600초 | 해당 단계의 큐 대기·실행 시간 포함 |
| 사용자별 GPU 메모리 할당·배치·다중 GPU | 없음 | 계정 데이터 접근 차단과 GPU 자원 분할은 별개 |

큐의 8개는 **사용자 8명**이나 **코디 8개**라는 보장이 아닙니다. 한 코디의 다음 옷도
다시 FIFO 큐에 들어갑니다. 다수 사용자가 한꺼번에 제출하면 중간 단계가 429로 실패할 수도 있습니다.
대기 순서는 노출하지만 사용자별 공정성, 코디 전체 슬롯 예약, 혼잡 시 재시도는 구현되지 않았습니다.
추천의 사용자별 분당 10회 제한은 추천 API의 제한이며 착샷 큐의 과다 점유를 막지 않습니다.

### 현재 속도와 계산상 처리량

실제 서버 로그의 2026-11-11 12:24~16:48 최근 9개 단계는
9.2, 8.5, 8.5, 9.2, 8.9, 8.9, 8.6, 8.0, 8.2초입니다. 평균 약 **8.67초/벌**입니다.
현재 프론트 제출은 기본 30단계 추론·샘플 1장을 사용하며 결과는 576×864입니다.
로그 시간은 모델 호출 구간만 재며 큐 대기, 의류 사진 유형 감지, 이미지 전달·저장·폴링은 제외합니다.

| 요청 | 모델 계산만의 대략적 시간/처리량 |
|---|---|
| 상의+하의 1코디 | 약 17초, 계산상 최대 약 3.46코디/분 |
| 아우터 포함 1코디 | 약 26초, 계산상 최대 약 2.31코디/분 |
| 5명이 아우터 포함 1개씩 | 총 15단계, 모두 끝나는 데 계산만 약 130초 |
| 9명이 아우터 포함 1개씩 | 총 27단계, 계산만 약 234초; 전부 접수된다는 보장 없음 |

위 값은 **관측된 단일 작업 속도에서 계산한 추정**이며 다중 사용자 부하 테스트 결과가 아닙니다.
실제 응답은 전송·유형 감지·폴링으로 더 느립니다. 초기 모델 로딩 및 첫 요청도 다를 수 있습니다.
지속적으로 처리량보다 많은 요청이 들어오면 대기열이 차고 실패합니다. 여유 VRAM만으로
동시 지원 인원이나 여러 worker의 안전성을 산정할 수 없습니다.

현장 VRAM 스냅샷은 전체 약 32,607MiB 중 사용 약 7,722MiB였습니다. 다른 프로그램과
할당 캐시도 포함한 순간 값이며 한 작업의 최대 메모리 사용량은 아닙니다.
코드는 peak VRAM을 계산하지만 현재 API 작업 기록에 보관하지 않습니다.
RTX 5090은 [NVIDIA MIG 지원 목록](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/supported-gpus.html)에
없으므로 사용자마다 하드웨어를 고정 분할하는 MIG 구성을 전제로 해서는 안 됩니다.
여러 모델 인스턴스를 띄우는 것은 별개의 소프트웨어 동시 실행 실험이며 고정 GPU 분할이 아닙니다.

화면의 `STEP_SECONDS=40`은 팀원의 RTX 3060 Ti 측정에서 온 값으로, 현재 5090의 ETA와
맞지 않습니다. 대기 인원과 최근 실측 시간을 반영하는 예상 시간 계산이 필요합니다.

### GPU 외 확장 한계와 다음 작업

- GPU 큐는 RAM에 있습니다. 완료 결과 보관 정책과 달리 **진행 중 작업은 재시작 시 이어서 실행되지 않습니다**.
- 고객의 전신 사진·생성 결과는 로그아웃 또는 30분 미사용까지 프로세스 RAM을 사용합니다.
  현재 계정/세션별 결과 개수·총 바이트 제한은 없어 장시간 많은 생성 시 CPU RAM도 관찰해야 합니다.
  이것을 해결하기 위해 사진을 임의로 DB·파일에 저장하면 기존 개인정보 정책과 충돌합니다.
- 큐에 들기 전 이미지 디코딩과 frontend Task 생성이 있으므로 대기 큐 8개만으로
  전체 요청 수·CPU 메모리까지 제한되는 것은 아닙니다.
- 고객 사진은 프로세스별 메모리이므로 웹 worker를 단순히 늘리면 요청마다 사진이 안 보일 수 있습니다.
  공유하는 RAM 저장소나 세션 고정 등 사진 정책을 지키는 설계가 선행되어야 합니다.
- 로컬 화면과 멘토 화면은 동일한 GPU 서버를 공유합니다. 각 화면에 별도 GPU 용량이 생기지 않습니다.
- 학습 전환은 착샷을 멈추고 실행 중 작업을 정리하는 방식으로, 학습과 착샷 간 GPU 분할이 아닙니다.

이후 사용자당 진행 중 코디 1개 제한, 전역 8개 접수 상한, 사용자별 순환 큐,
429 재시도 안내를 구현했습니다. 최신 동작은 [착샷 접수 정책](TRYON_QUEUE.md)을 참고합니다.
실측 ETA와 단계별 처리 시간도 이후 적용했습니다. 최신 결과는
[예상 시간 계산과 검증](TRYON_ETA_AND_LAYERING.md)에 있습니다. peak VRAM/CPU RAM의 지속 관측은 남아 있습니다.
그 뒤 합성 사진을 사용하는 격리된 2명/5명/8명 동시 테스트로 성공률과 p50/p95 완료 시간을
측정해야 합니다. 현재 상태에서 수십 명의 동시 착샷 완료를 보장할 근거는 없습니다.
