## 1. 제품의 목표와 핵심 결정

**사용자가 입고 싶은 옷을 지키면서, 저장한 스타일을 자신의 옷으로 재현하고, 하루 일정에 맞게 입는 방법까지 제안한다.**

추가할 세 기능을 하나의 추천 요청에서 함께 사용할 수 있게 만든다. 필수 의류 선택은 사용자의 의도를 고정하고, 참고 사진은 원하는 모습을 전달하며, 일정은 실제로 입을 수 있는 조건을 정한다. 사용자는 셋 중 하나만 입력해도 추천을 받을 수 있다.

사업적으로 검증할 가치는 ‘대학생에게 AI 코디를 제공한다’는 표현보다 구체적이어야 한다. 초기 가설은 **집에 다시 들르기 어려운 대학생이 수업·발표·아르바이트·약속을 오가는 날, 새 옷을 사지 않고 원하는 분위기를 구현하는 데 드는 고민과 시간을 줄인다**는 것이다. 대학생 전체가 이 문제를 강하게 느낀다고 가정하지 않고 실제 경험과 반복 사용으로 확인한다.

| 결정 | 제안 |
|---|---|
| 최초 대상 | 최근 한 달 SNS 스타일을 저장했고, 하루에 성격이 다른 일정이 두 개 이상 있었던 대학생 |
| 첫 사용 가치 | 자주 입는 옷 몇 벌만 등록하고, 저장한 사진 한 장을 내 옷으로 재현 |
| 반복 사용 가치 | 이미 등록한 옷과 하루 일정을 이용해 외출 전 코디를 빠르게 확정 |
| 추천 범위 | 기존 상의·하의·아우터 유지. 신발·가방·액세서리는 이번 범위에서 제외 |
| 일정 결과 | 같은 상의·하의를 유지하는 하루 코디와 일정별 아우터 착용 안내 |
| AI의 핵심 역할 | 사진의 시각적 특징과 자유로운 표현을 구조화하고 유사한 의류를 검색 |
| 정확성을 보장할 부분 | 소유권, 필수 의류, 제외 의류, 사용 가능 상태는 서버 규칙으로 검증 |
| 2D 착샷의 역할 | 추천을 고른 뒤 전체적인 색·형태를 확인하는 보조 수단 |
| 사업 판단 | 기능 만족도와 함께 실제 착용 결정, 재방문, 비용, 결제 행동을 측정 |

## 2. 경쟁 서비스와 차별성 가설

### 2.1 이미 겹치는 기능

에이클로젯은 공식 FAQ에서 선택한 옷을 유지하고 나머지 카테고리를 추천하는 기능을 설명한다. 따라서 ‘내가 고른 옷을 반드시 포함’하는 기능 자체를 독자적인 차별성으로 내세우기는 어렵다. [Acloset 공식 FAQ](https://www.acloset.app/support/)

에이클로젯은 보유 의류로 날씨·계획에 맞춘 추천, 가상 착샷, 날짜별 코디와 여행 계획도 안내한다. ‘일정 고려’, ‘AI’, ‘2D 착샷’이라는 단어만으로 경쟁 우위를 주장할 수 없다. [Acloset 공식 기능 소개](https://www.acloset.app/)

Whering도 디지털 옷장, 코디·룩북, 위시리스트·무드보드를 제공한다. 영감 이미지를 모으는 경험 역시 기존 서비스와 겹친다. [Whering 공식 기능 소개](https://whering.co.uk/how-it-works)

### 2.2 검증할 차별성

| 차별성 가설 | 사용자가 확인할 결과 | 입증 방법 |
|---|---|---|
| 내 옷 안에서 현실적으로 재현 | 참고 사진의 색·실루엣을 어떤 옷으로 대체했는지 확인 | 같은 옷장과 사진을 사용한 대조 평가 |
| 여러 일정의 충돌 해결 | 발표와 야외 이동을 고려한 한 벌, 구간별 아우터 안내 | 단일 상황 추천보다 하루 전체에 적합한지 평가 |
| 내 선택을 끝까지 보존 | 지정 의류가 모든 후보와 대체 추천에 유지 | 자동 검증과 실제 과제 성공률 |
| 재현의 한계를 설명 | 비슷한 부분, 다른 부분, 옷장에 없는 요소를 구분 | 사용자의 이해도·수정 횟수·신뢰도 측정 |
| 등록 부담 대비 빠른 효용 | 옷장 전체를 등록하기 전에 첫 유효 추천을 확인 | 가입부터 첫 코디 선택까지 시간·이탈 측정 |

경쟁 서비스가 이 흐름을 지원하지 않는다고 단정하지 않는다. 공식 안내만으로 세부 동작과 품질을 판별할 수 없으므로, 사용 가능한 동일 조건에서 직접 비교해야 한다. 경쟁 서비스에 해당 입력 방법이 없으면 그 사실과 대체 입력 과정을 기록하고, 임의로 품질 점수를 0점 처리하지 않는다.

**진입은 ‘저장한 스타일 재현’, 재사용은 ‘오늘 일정에 맞는 내 옷 선택’으로 설계한다.** 필수 의류 기능은 두 경험의 통제 수단이 된다. 복제하기 어려운 자산은 버튼 세 개 자체보다, 동의를 받아 축적한 ‘원하는 스타일 → 실제 보유 의류의 대체 관계 → 최종 선택과 착용 결과’의 품질이다. 초기에는 이런 자산이 아직 확보되지 않았다는 전제로 시작한다.

## 4. 원하는 옷을 필수로 포함하는 기능

### 4.1 사용 흐름

옷장 카드에 ‘이 옷으로 코디’ 버튼을 추가한다. 누르면 추천 화면에 해당 옷이 고정된 상태로 열린다. 추천 화면에서도 옷을 추가하거나 해제할 수 있다. 초기 화면은 한 벌 선택을 유도하되 API는 상의·하의·아우터에서 각각 한 벌씩, 최대 세 벌을 지원한다.

예를 들어 남색 셔츠를 지정하면 모든 결과의 상의 ID는 그 셔츠여야 한다. 참고 사진에 흰 티셔츠가 있어도 남색 셔츠를 바꾸지 않는다. 결과에는 ‘선택한 셔츠를 유지해 참고 사진의 상의 색과는 다릅니다’처럼 차이를 설명한다.

### 4.2 절대 조건과 충돌 처리

| 조건 | 처리 |
|---|---|
| 다른 사용자의 의류 또는 없는 ID | 존재 여부를 구분하지 않는 404 |
| 같은 카테고리의 서로 다른 두 벌 | 422, 해당 슬롯에서는 한 벌만 선택하도록 안내 |
| 필수 의류와 제외 의류가 겹침 | 422, 사용자가 어느 조건을 바꿀지 선택 |
| 필수 의류가 세탁 중·비활성·분류 미확정 | 추천하지 않고 상태 변경 또는 재분석을 안내 |
| 추천 도중 의류 삭제·상태 변경 | 저장 직전 재검증, 변경 충돌은 409 |
| 사용 가능한 조합이 한 개 또는 두 개 | 가능한 개수만 반환, 세 개를 채우려고 조건을 위반하지 않음 |
| 조건을 만족하는 조합 없음 | 422 `NO_FEASIBLE_OUTFIT`, 원인과 변경 가능한 조건 반환 |
| 엔진 오류·시간 초과 | 동일한 필수 조건을 적용하는 대체 추천, 불가능하면 동일한 충돌 응답 |

필수 아우터는 기본적으로 ‘계속 입기’로 취급한다. 사용자가 ‘실내에서는 벗어도 됨’을 선택한 경우에만 일정별로 벗는 안내를 허용한다. 이때도 추천의 아우터 ID는 유지되며, 결과에 ‘소지하지만 이 구간에서는 벗음’을 표시한다. 포함 여부와 실제 착용 상태를 혼동하지 않도록 한다.

**이 기능의 보장은 AI가 아닌 규칙의 책임이다.** AI가 순위를 제안하더라도 서버는 모든 결과에서 `required IDs ⊆ outfit IDs`를 검사한다. 현재 `SafeRecommender`, 서비스 저장 직전 대체 경로, 프론트 mock까지 함께 수정해야 한다.

### 4.3 완료 기준

정상·대체·오류 복구 경로에서 반환하는 유효 코디의 필수 의류 포함률 100%를 자동 테스트로 확인한다. 이는 규칙 검증 기준이며 사용자의 미적 만족도 100%를 뜻하지 않는다. 추가 입력이 없는 기존 추천 요청은 기존 동작을 유지한다.

## 5. 하루 일정에 맞춘 추천

### 5.1 첫 버전 입력

첫 버전은 오늘 또는 선택한 하루의 일정을 간단한 카드로 입력한다. 학교 포털·에브리타임·구글 캘린더 자동 연동은 제외한다. 외부 연동 없이도 일정 추천의 가치를 먼저 검증할 수 있다.

| 필드 | 입력 방식과 의미 |
|---|---|
| 날짜와 시간대 | 날짜 선택, 기본 `Asia/Seoul`, 저장은 시간대가 있는 시각 |
| 시작·종료 시각 | 필수. 시작이 종료보다 이른지 확인 |
| 활동 | 수업, 발표, 면접, 아르바이트, 운동, 약속, 기타 |
| 환경 | 실내, 실외, 혼합, 모름 |
| 야외 노출 | 혼합이면 대략적인 야외 시간. 이동 구간도 선택 입력 |
| 활동 강도 | 낮음, 보통, 높음. 사용자가 수정 가능 |
| 중요도 | 보통 또는 우선 고려 |
| 복장 조건 | 명시된 드레스코드가 있을 때만 사용자 확인으로 추가 |
| 기온 | 시간대 예보 또는 수동 범위, 실내는 사용자가 아는 경우만 입력 |

하루 최대 10개 일정으로 시작한다. 겹치는 시각은 오류와 함께 수정하도록 하고, 자정을 넘는 일정은 날짜를 포함해 두 구간으로 나눠 확인한다. 장소의 정확한 주소나 수업명·교수명은 추천에 필요하지 않으면 수집하지 않는다.

‘발표’라는 단어만 보고 정장을 필수로 만들지 않는다. 일반적인 격식 정도는 부드러운 선호 조건으로 취급하고, 사용자가 확인한 구체적인 복장 제한만 강제한다. 현재 스타일 태그만으로 실제 드레스코드 준수를 보장할 수 없으므로 불확실한 속성은 확인 대상으로 남긴다.

### 5.2 AI 입력 보조

구조화 입력이 작동한 다음 ‘오전 수업, 오후 발표, 저녁에 야외 동아리 활동’처럼 자유 문장을 입력할 수 있게 한다. AI는 일정의 초안을 만들고, 빠진 시각·실내외 여부·복장 제한은 `unknown`으로 반환한다. 사용자가 확인한 카드만 추천에 전달한다.

시간표 이미지 인식은 후속 범위로 둔다. 이미지에서 시간과 활동을 추출하더라도 실내 온도나 사용자의 이동 경로까지 추정하지 않는다. 문장 입력보다 실제로 시간을 줄이는지 확인한 뒤 도입한다.

### 5.3 추천 방식

초기 출력은 갈아입을 여분의 상·하의를 요구하지 않는 **하나의 기본 코디와 아우터 착용 계획**이다. 일정이 여러 개라는 이유로 매 일정마다 다른 코디를 생성하지 않는다.

예시 입력은 ‘오전 실내 수업 → 오후 발표 → 저녁 야외 이동’이다. 출력은 같은 셔츠·하의를 유지하면서 수업 중 아우터를 벗고, 이동 중 입는 계획이다. ‘발표에 적합함’과 ‘야외 시간대의 보온을 고려함’을 각각 근거로 보여 준다.

평가는 다음 순서로 한다.

1. 사용자 소유·사용 가능 상태·필수 의류·명시한 복장 제한을 확인한다.
2. 각 일정에서 아우터를 입는지에 따라 조합의 적합도를 계산한다.
3. 일정별 적합도의 가중 평균과 가장 부적합한 일정의 점수를 함께 반영한다.
4. 중요한 짧은 발표가 긴 일상 수업에 묻히지 않도록 ‘우선 고려’ 구간을 별도로 반영한다.
5. 충족하지 못하는 조건을 반환하고 사용자의 변경 없이 제한을 풀지 않는다.

검증 전 시작 식은 `일정 점수 = 0.6 × 가중 평균 적합도 + 0.4 × 최저 구간 적합도`로 제안한다. 시간·중요도 가중치는 상한을 두고 실험으로 조정한다. 사람의 실제 체감 온도나 의류의 보온성을 정밀하게 측정한 공식으로 홍보하지 않는다.

### 5.4 날씨 처리와 실패 대응

현재 자동 날씨는 현재 기온을 제공한다. 오늘 밤이나 내일 일정에 현재 값을 복사해 예보로 표시하지 않는다. 시간대별 예보가 도입되기 전에는 수동 기온 범위를 입력받고, 이후에도 자료의 기준 시각·출처·적용 시간대를 저장한다.

실내 온도는 외부 날씨로 알 수 없으므로 임의의 고정 온도를 사용하지 않는다. ‘실내 온도 미입력’ 상태에서는 활동·격식과 아우터 탈착 위주로 판단한다. 예보 실패 시 수동 입력으로 이어지고, 날씨를 모르는 상태의 추천은 제한된 근거를 화면에 표시한다.

격식 있는 행사와 격한 운동을 같은 옷으로 모두 해결할 수 없으면 ‘복장 변경이 필요할 수 있음’을 안내한다. 여분 옷을 챙기거나 귀가하는 다중 코디 최적화는 후속 확장으로 남긴다.

## 6. 저장한 사진의 스타일을 내 옷으로 재현

### 6.1 사용 흐름

1. 휴대폰에서 SNS 캡처 또는 저장 이미지를 한 장 선택한다.
2. 기존 이미지 표준화 경로로 방향·형식을 처리하고 필요한 옷 영역을 자른다.
3. 사람이 여러 명이면 어느 인물의 옷인지 선택한다. 상·하의가 보이지 않으면 추가 자르기 또는 부분 재현을 안내한다.
4. 분석된 색상·패턴·실루엣·레이어 특징을 확인하고, 사용자가 원하는 부분을 고른다.
5. 본인 옷장에서 후보를 찾고 필수 의류와 일정 조건을 함께 적용한다.
6. 최대 세 개 코디에 ‘닮은 점’, ‘대체한 점’, ‘재현하지 못한 점’을 표시한다.
7. 사용자가 고른 코디에 대해서만 선택적으로 2D 착샷을 생성한다.

인스타 계정 로그인이나 링크 수집·크롤링은 첫 버전에 포함하지 않는다. 업로드 이미지와 필요한 의류 영역만 처리한다. 참고 이미지 속 옷을 새 소유 의류처럼 옷장에 자동 추가하지 않는다.

### 6.2 분석 정보와 사용자의 통제

| 정보 | 예시 | 사용 방식 |
|---|---|---|
| 카테고리별 영역 | 상의, 하의, 아우터 | 본인 옷장의 동일 카테고리 후보와 비교 |
| 색 구성 | 밝은 상의, 짙은 하의, 올리브 아우터 | 개별 색과 조합의 명암 대비 평가 |
| 형태 | 여유 있는 상의, 직선형 하의, 짧은 아우터 | 실루엣 특징. 가려졌으면 미확정 |
| 패턴과 시각적 질감 | 무지, 체크, 케이블 니트 느낌 | 이미지에서 보이는 특징만 추출 |
| 레이어 | 아우터가 열려 이너가 보임 | 조합·착샷의 상의 보존 설정에 사용 |
| 분위기 | 단정한 캐주얼 등 | 표준 태그와 보조 설명으로 구조화 |
| 사용자의 우선 요소 | 색감 또는 형태 또는 전체 분위기 | 참고 점수 내부의 가중치 선택 |

사진으로 실제 소재·치수·두께를 확정하지 않는다. 사람의 얼굴·신원·체형 유사도를 스타일 점수에 넣지 않는다. 모델 점수는 정확도 확률로 포장하지 않고, 검증 전에는 ‘확인 필요’ 여부와 추출 근거로 전달한다.

### 6.3 추천 기술

현재의 색상·패턴·스타일 태그를 이용한 규칙 검색을 기준선으로 먼저 만든다. 그다음 사진과 옷을 비교할 수 있는 **임베딩**을 추가한다. 임베딩은 이미지의 시각적 특징을 숫자 벡터로 표현한 것으로, 텍스트 태그가 완전히 같지 않아도 비슷한 형태를 찾는 데 사용한다. CLIP 연구는 이미지와 언어를 연결하는 표현 학습을 제시한다. [CLIP 원 논문](https://proceedings.mlr.press/v139/radford21a.html)

기존 비전 코드의 CLIP을 먼저 비교 대상으로 활용하고, 패션 도메인에 맞춘 FashionCLIP 계열을 후보로 평가한다. 패션 표현 학습의 연구 근거가 있어도 제품 사진과 SNS 착용 사진 사이의 차이를 자동으로 해결한다는 뜻은 아니다. 우리 입력의 검색·코디 품질, 모델·가중치 이용 조건과 자원 소모를 확인한 뒤 채택한다. [FashionCLIP 저자 저장소](https://github.com/patrickjohncyh/fashion-clip)

처리는 ‘참고 사진의 의류 영역 분리 → 슬롯별 유사 후보 검색 → 전체 코디의 조화 평가 → 일정 및 필수 조건 검증’ 순서다. 가장 비슷한 상의·하의·아우터를 각각 독립적으로 고르는 것만으로는 어울리는 코디가 보장되지 않는다.

참고 사진 전체에 대한 단일 벡터 비교는 배경·포즈·인물의 영향을 받을 수 있다. 주된 비교 대상은 의류 영역으로 제한하고, 색·패턴·형태별 유사도와 전체 조합 점수를 함께 사용한다. 동일한 모델·전처리 버전으로 만들어진 벡터만 비교한다.

### 6.4 불완전한 재현 처리

예를 들어 사진의 검정 가죽 재킷이 옷장에 없으면 남색 재킷을 제안할 수 있다. 이때 ‘어두운 짧은 아우터의 비율은 유지하지만 가죽 질감은 재현되지 않음’이라고 설명한다. 근거 없이 ‘92% 동일’처럼 숫자를 표시하지 않는다.

입을 수 없는 신발·가방 요소가 사진에서 스타일의 핵심이면 현재 지원 범위 밖임을 표시한다. 아우터가 이너를 가리거나 한 벌만 보이는 경우에는 보이는 부분만 재현한다. 분석 실패 시 사용자가 색·분위기를 직접 선택하도록 하고, 이를 사진 AI 재현 성공으로 집계하지 않는다.

## 7. AI를 사용하는 이유와 검증 방법

### 7.1 작업별 책임

| 작업 | 구현 수단 | AI의 필요성을 판단할 증거 |
|---|---|---|
| 지정 의류 포함, 소유권·세탁 상태 확인 | 결정적 규칙·DB 검사 | AI가 필요하지 않음. 모든 경로의 불변 조건으로 보장 |
| 구조화된 일정의 시간·충돌 계산 | 규칙·제약 최적화 | 일정 입력만으로 해결 가능. AI 성과로 주장하지 않음 |
| 자연어 일정의 활동·환경 추출 | 선택적 언어 모델 | 수동 카드 대비 입력 시간과 수정 부담 감소 |
| 사진의 의류·형태·분위기 추출 | 비전 모델 | 수동 입력과 단순 색상·태그보다 적은 노력으로 유용한 정보 확보 |
| 사진과 내 옷의 유사도 검색 | 이미지·언어 임베딩 | 태그 기준선보다 재현 평가와 최종 선택률 개선 |
| 코디 순위 결정 | 규칙 점수 우선, 필요하면 학습 모델 | 같은 후보 집합에서 순위 품질이 추가로 개선될 때 도입 |
| 추천 이유 표시 | 계산 근거를 템플릿으로 표시 | 설명 문장만 자연스러워진 것은 추천 품질 개선이 아님 |
| 2D 착샷 | 기존 생성 모델 | 코디 결정 도움과 실제 옷 차이를 별도로 측정 |

**입증할 주장은 ‘AI가 없으면 서비스가 불가능하다’가 아니라, 사진과 자유로운 표현을 이해하는 부분에서 AI가 규칙 기반 방법보다 사용자 노력과 결과 품질을 얼마나 개선하는가이다.**

### 7.2 비교 실험

| 비교 | 같은 조건으로 유지할 것 | 측정 |
|---|---|---|
| 규칙 참고 검색 대 임베딩 추가 | 옷장·참고 사진·제약·결과 개수 | 재현 적합도, Top 3 중 수용 가능한 코디 비율 |
| 기존 단일 상황 대 일정 전체 고려 | 같은 옷장·실제 하루 일정 | 하루 전체 적합도, 부적합한 구간 수 |
| 수동 일정 카드 대 AI 초안 | 입력해야 할 정보와 확인 절차 | 확인 완료까지 시간, 수정 횟수, 잘못 확정된 필드 |
| 동일 후보의 규칙 순위 대 AI 순위 | 후보 집합과 추출 속성 | 선호되는 순위, 추가 지연·비용 |
| 코디 카드 대 코디 카드와 착샷 | 동일 추천과 의류 | 확정까지 시간, 선택의 확신, 생성 오류로 인한 오판 |

현재 비전에도 AI가 있으므로 ‘local 전체 대 AI 전체’를 비교하며 비AI 기준선이라고 부르면 안 된다. 추천 순위를 평가할 때는 공통 속성과 제약을 고정해 AI를 추가한 부분의 효과만 분리한다. 추출 효과는 별도 실험에서 사람이 확인한 속성과 비교한다.

평가에서 모델 이름을 가리고 결과 순서를 섞는다. 두 결과가 같으면 차이를 만든 것처럼 집계하지 않는다. 동일 사진·동일 사용자의 반복 응답은 독립 표본처럼 세지 않고 참가자 단위로 요약한다. 튜닝에 사용한 사람·옷·참고 사진과 최종 평가 세트를 분리한다.

### 7.3 모델 도입 범위

처음부터 자체 대형 모델을 학습하지 않는다. 기존 속성 추출과 사전 학습 임베딩, 검증 가능한 점수 조합으로 시작한다. 언어 모델은 일정 초안과 모호한 스타일 표현의 구조화에 제한적으로 사용하며, 모델 이름·공급자는 어댑터와 버전으로 관리한다. 계정에서 사용 가능한 모델과 비용은 구현 시 공식 정보와 실제 호출로 확인한다.

사용자가 선택한 결과가 누적돼도 수락·거절만으로 실제 착용이나 선호 이유를 단정하지 않는다. 충분한 데이터와 독립 평가를 확보한 뒤 소규모 순위 학습을 검토한다. 사용자 사진과 일정을 기본 학습 데이터로 사용하지 않는다.

| 5 | 슬롯별 후보 검색, 필수 슬롯 고정 | A, B의 특징 사용 |
| 6 | 후보 조합 생성, 일정별 착용 상태 평가 | A |
| 7 | 색상·상황·선호·참고 유사도·일정 점수 계산 | A |
| 8 | 조건을 지키는 서로 다른 코디 최대 세 개 선택 | A |
| 9 | 최신 의류 상태로 다시 검증하고 결과·근거 저장 | C |
| 10 | 차이와 일정별 안내를 표시, 사용자가 최종 선택 | D |
| 11 | 선택한 코디만 기존 GPU 착샷 대기열에 접수 | D, C |
| 12 | 선택·실제 착용·불만 이유를 구분해 기록 | C, D |

시간이 긴 AI·네트워크 호출 동안 DB 행 잠금을 유지하지 않는다. 현재 추천 서비스처럼 입력을 읽어 처리한 뒤 저장 직전 상태를 재확인하는 흐름을 유지한다. 필수 의류가 그 사이 세탁 상태로 바뀌면 다른 옷으로 몰래 교체하지 않는다.

### 8.2 점수 설계

모든 절대 조건을 만족하는 후보에만 점수를 매긴다. 조건 위반에 큰 감점만 주는 방식은 금지한다. 상대적 선호 점수는 다음처럼 0~100으로 맞추고, 모델의 코사인 유사도를 확률이나 그대로의 100점 척도로 취급하지 않는다.

| 항목 | 의미 |
|---|---|
| C 색 조화 | 후보 코디 안에서 의류끼리 어울리는 정도 |
| O 단일 상황 | 기존 선택 상황에 맞는 정도 |
| P 개인 선호 | 지원되는 선호 스타일과의 일치 |
| S 일정 적합 | 하루의 여러 구간에서 실제로 입기 적합한 정도 |
| R 참고 재현 | 참고 이미지의 선택한 특징을 재현한 정도 |

검증 전 시작 가중치는 다음과 같다. 유효한 선호 입력이 없는 신규 경로에서는 P를 제외하고 나머지를 합계 100으로 재정규화한다.

| 요청 | C | O | P | S | R |
|---|---:|---:|---:|---:|---:|
| 기존 요청 또는 필수 의류만 추가, 지원 선호 있음 | 28 | 42 | 30 | 0 | 0 |
| 기존 요청 또는 필수 의류만 추가, 지원 선호 없음 | 40 | 60 | 0 | 0 | 0 |
| 일정 추가 | 20 | 0 | 20 | 60 | 0 |
| 참고 사진 추가 | 15 | 20 | 15 | 0 | 50 |
| 일정과 참고 사진 추가 | 15 | 0 | 15 | 35 | 35 |

일정이 있으면 O를 별도로 합산하지 않아 상황 점수의 중복 반영을 줄인다. R의 색상 유사도는 참고 사진과 닮았는지, C는 후보 내부의 색 조화인 만큼 목적을 나눠 평가한다. 가중치는 성능 주장이 아닌 실험 시작값이고, 고정 평가 세트를 보고 계속 튜닝하지 않는다.

‘우선 고려’ 일정이나 확인된 드레스코드는 가중치만 높여 해결하지 않는다. 필수 제한은 먼저 검사하고, 충족 가능한 후보 사이에서만 미적 점수를 비교한다. 실제 격식·보온도 판단이 불확실하면 완벽히 충족한다고 설명하지 않는다.

### 8.3 후보 수와 성능

현재 전체 조합 생성은 옷장 크기가 커질수록 비용이 커진다. 새 경로는 슬롯별 유사·적합 후보를 우선 가져오고 필수 의류는 항상 포함한다. 예를 들어 슬롯별 20개라면 최대 `20 × 20 × (20 + 1) = 8,400`개 조합에서 시작할 수 있다. 이 숫자는 초기 실험 설정이다.

상위 후보를 자른 뒤 조건을 만족하지 못했다고 전체 옷장에 답이 없다고 단정하지 않는다. 후보 범위를 늘려 재검색하고, 시간 한계로 탐색을 마치지 못하면 탐색 실패와 실제 조건 불가능을 구분한다. 대체 규칙 검색은 필수 의류와 상태 검사를 계속 유지한다.

마지막에는 의류 ID 조합의 중복을 제거하고, 조건이 허용하면 서로 다른 대안을 고른다. 세 개를 다양하게 만들기 위해 필수 옷을 바꾸지는 않는다. 정렬 동점 기준을 고정해 테스트를 재현할 수 있게 한다.

### 8.4 캐시와 GPU

추천 캐시에는 사용자 ID, 옷장·속성 버전, 필수·제외 의류, 일정 버전, 날씨 기준 시각, 참고 이미지 특징 버전, 점수 정책 버전을 반영한다. 다른 사용자의 결과를 재사용하지 않으며 JWT·개인 원문을 로그에 넣지 않는다.

의류 임베딩은 업로드·이미지 변경 시 비동기로 계산하고 모델 버전별로 보관한다. 기존 의류는 처음 필요할 때 또는 제한된 배치로 보강한다. 이미지가 바뀌지 않아도 사용자가 속성을 수정하면 관련 특징·추천 캐시를 갱신한다.

한 대의 GPU를 공유하므로 신규 비전 작업을 착샷 서버 옆에서 무제한 병렬 실행하지 않는다. 우선 기존 경량 모델의 CPU 처리와 캐시를 측정하고, GPU가 필요하면 공통 자원 제한 또는 별도 예약된 작업 구간을 둔다. 기존 착샷의 사용자당 한 개·전체 접수 제한·공정 대기열은 유지한다.

2D 착샷 캐시에는 사용자·전신 사진 버전·의류 이미지 버전·착용 의류 ID·아우터 상태·모델과 레이어 처리 버전을 넣는다. 아우터를 벗은 구간은 별도 결과일 수 있으므로 요청한 경우에만 생성한다. 추천 세 개와 모든 일정 구간을 자동으로 생성하지 않는다.

## 9. API와 데이터 계약 변경안

### 9.1 기존 추천 API의 확장

`POST /api/v1/recommendations`를 유지하고 선택 필드를 추가한다. 지금 요청 스키마는 알 수 없는 필드를 거부하므로 **백엔드와 공통 계약을 먼저 배포한 뒤 프론트가 새 필드를 보내도록** 한다.

| 새 필드 | 형식 | 기본 동작 |
|---|---|---|
| `required_garment_ids` | UUID 배열, 최대 3개 | 빈 배열이면 기존 추천 |
| `outerwear_policy` | `always_worn` 또는 `removable` | `always_worn` |
| `schedule_id` | 본인 일정 UUID 또는 null | 없으면 기존 단일 상황 |
| `schedule_version` | 일정의 정수 버전 | ID가 있을 때 필수, 오래된 화면이면 409 |
| `reference_id` | 본인 참고 스타일 UUID 또는 null | 없으면 이미지 유사도 제외 |
| `reference_version` | 참고 스타일의 정수 버전 | ID가 있을 때 필수 |

기존 `lat/lon` 또는 `temperature_c` 입력 계약은 유지한다. 일정별 기온은 일정 문맥의 별도 자료이며, 대표 현재 기온을 모든 일정에 복사하지 않는다. 기온 입력 계약을 바꿀 필요가 생기면 별도 버전으로 다룬다.

일정·참고 스타일의 실제 내용과 특징은 서버가 소유권을 확인해 가져온다. 프론트가 임의의 사용자 ID, 다른 옷장의 벡터, 계산된 적합도 점수를 넣을 수 없게 한다.

예시 요청:

```json
{
  "temperature_c": 12,
  "occasion": "daily",
  "preferred_styles": ["minimal"],
  "excluded_items": [],
  "required_garment_ids": ["11111111-1111-4111-8111-111111111111"],
  "outerwear_policy": "removable",
  "schedule_id": "22222222-2222-4222-8222-222222222222",
  "schedule_version": 1,
  "reference_id": "33333333-3333-4333-8333-333333333333",
  "reference_version": 1
}
```

공통 계약 `2.0`은 기본값을 가진 선택 필드를 추가하는 `2.1`을 목표로 한다. 현재 `Outfit.items`, 결과 최대 세 개, 과거 `shoes` 조회 호환성을 유지한다. 내부 `UserContext`에는 검증 완료된 일정·참고 특징을 전달하고, 원본 이미지나 외부 API 키를 넣지 않는다.

응답에는 선택적으로 `constraint_checks`, `score_components`, `wearing_plan`, `reference_matches`, `limitations`, `policy_version`을 추가한다. 점수 구성은 설명·디버깅용이며 초기 UI는 정확한 확률처럼 표시하지 않는다. 기존 레코드는 새 필드가 없어도 조회할 수 있게 한다.

### 9.2 보조 API

| API 제안 | 동작 |
|---|---|
| `POST /api/v1/day-plans` | 사용자가 확인한 하루 일정 저장 |
| `GET /api/v1/day-plans` 및 `/{id}` | 본인 일정 목록·상세 |
| `PATCH /api/v1/day-plans/{id}` | 기대 버전을 확인하고 일정 수정 |
| `DELETE /api/v1/day-plans/{id}` | 일정과 관련 개인 문맥 정리 |
| `POST /api/v1/day-plans/parse` | 자연어를 저장되지 않은 일정 초안으로 변환 |
| `POST /api/v1/style-references` | 이미지 업로드, 202와 분석 작업 ID 반환 |
| `GET /api/v1/style-references/{id}` | 대기·분석 중·확인 필요·완료·실패 상태 조회 |
| `PATCH /api/v1/style-references/{id}` | 추출 특징·관심 요소를 확인하고 버전 갱신 |
| `DELETE /api/v1/style-references/{id}` | 원본·파생 파일·벡터·관련 문맥 정리 |
| `POST /api/v1/recommendations/{id}/outcomes` | 본인 코디의 선택·실제 착용 결과 기록 |

기존 좋아요·별로예요 피드백 API는 유지한다. ‘좋아요’, ‘오늘 입기로 결정’, ‘실제로 입음’은 서로 다른 이벤트로 저장한다. 단순 코디 선택만으로 세탁 횟수를 증가시키지 않는다. 실제 착용 확정이 기존 착용 기록과 중복 반영되지 않도록 한다.

새 분석 엔드포인트에도 사용자별 요청 제한과 전체 처리량 제한을 둔다. 추천의 기존 분당 10회 제한은 유지하고, 업로드 제한은 이미지 크기·처리시간 측정 후 별도로 정한다. 중복 탭·모바일 재시도에는 사용자 범위의 멱등 키를 적용한다.

오류는 404 소유 리소스 없음, 409 버전·상태 변경, 422 입력 충돌·확인된 불가능 조건, 429 제한 초과, 503 일시적 처리 불가로 나누고 기존 오류 응답 형식에 코드를 추가한다. 처리 실패를 유효한 추천처럼 저장하지 않는다.

### 9.3 데이터 저장

| 데이터 | 최소 필드와 용도 |
|---|---|
| `day_plans` | 사용자, 날짜, 시간대, 버전, 생성·수정 시각 |
| `day_plan_events` | 일정 ID, 시작·종료, 활동, 환경, 중요도, 확인된 제한 |
| `style_references` | 사용자, 분석 상태, 저장 정책·만료, 특징 JSON, 모델·전처리 버전 |
| `garment_visual_features` | 의류 ID, 이미지 버전, 모델 버전, 임베딩, 보조 속성, 추출 시각 |
| 기존 추천 문맥 | 필수·제외 IDs, 최소 일정 요약, 참고 특징 버전, 날씨 출처, 점수 정책 |
| 추천별 상세 근거 | 슬롯별 유사 요소, 일정별 착용 상태, 제한·대체 사유 |
| `recommendation_outcomes` | 사용자, 추천·코디 ID, 선택·착용 상태, 시각, 중복 방지 키 |
| 최소 운영 지표 | 처리시간·오류 종류·캐시 적중·GPU 초·사용량. 사진과 일정 원문 제외 |

초기 개인 옷장 규모에서는 정규화한 벡터를 소유 사용자 범위로 읽어 메모리에서 비교할 수 있다. 벡터 DB나 `pgvector` 도입을 필수 선행 작업으로 두지 않는다. 규모가 커져 조회 비용이 문제일 때 인덱스를 검토한다.

마이그레이션은 신규 테이블·nullable 또는 기본값 있는 필드 추가로 진행한다. 기존 계정, 의류 ID·속성·파일, 추천·피드백을 재생성하지 않는다. 현재 마이그레이션의 실제 마지막 revision을 확인해 새 revision을 연결하고 번호를 미리 덮어쓰지 않는다.

## 10. 모바일 화면과 개인정보 처리

### 10.1 화면 구성

홈에는 ‘이 옷으로 코디’, ‘오늘 일정에 맞추기’, ‘저장한 스타일 재현’ 진입점을 둔다. 모두 같은 추천 화면을 사용하며 선택한 조건을 상단에 요약한다. 세 입력을 모두 강제로 요구하지 않는다.

결과 카드의 표시 순서는 다음과 같다.

1. 실제 옷장 의류 사진과 고정한 옷 표시.
2. 참고 스타일과 닮은 부분·다른 부분.
3. 일정별 입기·벗기 안내와 고려하지 못한 조건.
4. ‘이 코디 선택’, 선택적 ‘착샷 보기’, ‘조건 수정’.

필수 옷 선택은 되돌아가도 유지하고, 참고 사진을 다시 올리지 않고 우선 요소를 수정할 수 있게 한다. 사진 업로드는 기존 JPG·HEIC 표준화와 모바일 자르기 흐름을 재사용한다. 사진에 여러 사람이 있거나 일부가 잘린 경우도 명확한 안내로 복구할 수 있어야 한다.

### 10.2 데이터 최소화와 삭제

2026-11-13 사용자 요청으로 보관 정책을 확정했다. 참고 사진은 일회성 분석 자료이며 업로드 후 영역 선택용으로 최대 30분만 임시 보관한다. 선택한 영역을 한 번에 읽은 뒤 원본 접근을 차단하고 삭제 처리한 다음 분석한다. 분석하지 않은 사진과 비정상 종료로 남은 임시 파일도 만료 정리한다. 서버가 종료된 동안의 삭제는 다음 실행 시 수행하며 파일 삭제 실패는 재시도한다.

색상·패턴·옷 종류·스타일 키워드는 본인이 삭제하거나 탈퇴할 때까지 장기 보관해 추천에 재사용한다. 사진·의류 영역 좌표·이미지 미리보기·얼굴 특징은 장기 보관하지 않는다. 업로드 화면에 사진 처리 시점과 키워드 보관 기간, 삭제 방법을 안내한다. 초기 제안의 ‘미리보기·특징 최대 24시간/명시적 장기 저장’ 방식은 이 정책으로 대체한다.

분석 전에 얼굴과 SNS 계정명 등 불필요한 부분을 제외하도록 자르기를 제공하고, 외부 모델을 사용한다면 의류 영역만 전송하는 경로를 우선한다. 얼굴 임베딩·신원 추정은 생성하지 않는다. 사용자에게 외부 처리 여부와 보관 정책을 알리고, 공급자 측 보관까지 검증하지 않은 상태에서 ‘어디에도 저장되지 않는다’고 표현하지 않는다.

일정에는 필요한 활동·시간·실내외 정도만 저장한다. 외부 모델에 이메일·JWT·정확한 주소를 전달하지 않는다. 사진이나 일정에 쓰인 지시문은 분석 대상 데이터이며, 서버 명령·파일 접근·외부 URL 요청으로 실행하지 않는다.

새 일정·참고 사진 삭제는 DB 참조를 끊는 것만으로 끝내지 않는다. 파일·썸네일·벡터·캐시·추천 문맥에 복사된 민감한 요약까지 추적해 삭제하거나 비식별화한다. 기본 코디의 의류 ID 이력은 개인 일정 원문 없이 유지할 수 있다. 삭제 직후 조회를 차단하고 파일 정리 실패는 기존 삭제 작업 패턴으로 재시도한다.

기존 전신 사진 보관·삭제 정책은 유지한다. 이 확장에서 사용자의 과거 첨부 전신 사진을 테스트 자료로 가져오지 않는다. 개발 시 합성 인물과 사용 허락을 받은 의류·참고 자료를 사용한다. 기존 소스 파일 접근 차단도 유지한다.

## 11. 사업성 검증과 수익 구조

### 11.1 기능 소개 전에 확인할 문제

서비스 체험 전 설문에서는 다음 경험을 먼저 묻는다. 기능 설명 뒤 호감이 생긴 것과 원래 겪던 문제를 구분하기 위해서다.

- 최근 한 달 입고 싶은 특정 옷을 먼저 정한 날이 있었는가. 다른 옷을 고르는 데 얼마나 걸렸는가.
- 하루 중 수업·일·약속에 필요한 옷이 달라 곤란했던 구체적 경험이 있는가.
- SNS에 저장한 스타일을 실제로 따라 입어 봤는가. 못 했다면 무엇이 어려웠는가.
- 지금은 어떻게 해결하며, 그 과정에서 새 옷 구매·갈아입기·포기를 했는가.

그다음 같은 수준의 설명과 예시로 세 기능과 2D 착샷을 제시하고, 가장 필요한 한 가지와 사용하지 않을 이유를 묻는다. ‘AI’라는 이름의 선호와 기능 자체의 필요성을 분리한다. 사전 설문의 사용 의향·희망 가격은 수요 가설이며 실제 재사용이나 지불의 증거가 아니다.

### 11.2 단계별 검증

| 단계 | 제안 규모 | 얻을 증거 |
|---|---|---|
| 문제 인터뷰 | 조건에 맞는 대학생 8~12명 | 최근 사건, 기존 해결법, 등록 부담, 대체재 |
| 체험 전 설문 | 여러 학교·학년에서 60~100명 탐색 표본 | 문제 빈도와 기능별 우선순위, 가격 가설 |
| 과제형 사용성 실험 | 12~16명 | 입력·수정·추천 확정까지의 실제 실패 지점 |
| 비교 및 반복 사용 | 30~40명, 최소 2주 | 규칙·AI 비교, 코디 선택과 실제 착용, 주간 재사용 |
| 유료 검증 | 실제로 반복 사용한 사람 대상 | 고지된 이용량·가격에서 결제 또는 명확한 유료 신청 행동 |

이는 모집·개발 여건을 고려한 탐색 규모이며 통계적 충분성을 보장하는 표본 수가 아니다. 초기 분산과 효과 크기를 얻은 뒤 중요한 비교의 표본 수를 다시 정한다. 학교·패션 관심도·성별 표현·보유 옷 수에 편중되지 않게 모집하고 결과에는 참가자 수와 모집 조건을 함께 적는다.

### 11.3 지표와 진행 판단

아래 수치는 구현 전 임시 판단 기준이다. 파일럿의 실제 분포를 본 뒤 본 평가 전에 확정하며, 결과가 나온 후 유리하게 바꾸지 않는다.

| 구분 | 정의 | 제안 기준 |
|---|---|---|
| 조건 신뢰성 | 반환된 유효 코디 중 필수 의류·소유권·상태 조건을 모두 지킨 비율 | 자동 테스트 100%, 사용자 간 접근 허용 0건 |
| 재현 효용 | 참고 요청 중 상위 세 개에 하나 이상 수용 가능한 코디가 있는 비율 | 같은 조건의 태그 기준선보다 15%p 개선을 목표 |
| 일정 효용 | 사용자가 하루 모든 주요 일정에 입을 수 있다고 평가한 비율 | 단일 상황 기준선보다 15%p 개선을 목표 |
| 입력 부담 | 조건 입력 시작부터 확인 완료까지의 중앙 시간 | AI 초안이 수동보다 20% 이상 단축, 오류 확정률은 증가하지 않음 |
| 첫 사용 | 유효 옷장에 도달한 사용자 중 첫 코디를 선택한 비율 | 이탈 구간과 선택률을 함께 기록, 등록 전 이탈도 별도 분모로 공개 |
| 반복 사용 | 첫 코디 선택 후 8~14일 사이 다른 날 코디를 다시 선택한 사용자 / 첫 선택 사용자 | 탐색 기준 30%, 표본 수·불확실성과 함께 판단 |
| 실제 행동 | 주간 사용자 중 추천 코디를 한 번 이상 실제로 입었다고 확인한 비율 | 좋아요와 구분, 자기보고임을 명시 |
| 비용 효율 | 추가로 수용된 코디 한 건당 AI·연산 증가 비용 | 요금 가설 안에서 감당 가능한지 판단 |

재현 점수는 모델이 자신의 출력을 평가한 값만으로 판정하지 않는다. 실제 사용자와 별도 평가자가 색·형태·분위기·착용 가능성을 나누어 평가한다. 평균만 보고 특정 옷 유형이나 옷이 적은 사용자의 실패를 숨기지 않는다.

주간 핵심 지표는 **추천을 통해 실제 입을 코디를 확정한 사용자 수와 사용자당 확정한 날 수**로 제안한다. GPU 착샷 생성 수는 비용·활용 지표이며 제품 성공 지표를 대신하지 않는다.

### 11.4 수익 모델 가설

기본 옷장·필수 의류 추천으로 첫 효용을 제공하고, 고급 참고 스타일 재현·일정 저장·착샷 이용량을 유료 구독 또는 이용권으로 묶는 방식을 비교한다. 초기부터 옷 등록을 과하게 제한해 핵심 경험에 도달하지 못하게 하지는 않는다.

대학생이 얼마나 지불하는지는 아직 확인되지 않았으므로 적정 구독료를 단정하지 않는다. 기능과 월 사용량이 같은 조건에서 예를 들어 월 2,900원·4,900원·6,900원 같은 **실험용 가격 후보**를 비교할 수 있다. 이는 시장 가격 조사 결과가 아니다. 한 사람에게 낮은 가격부터 계속 제시하는 방식 대신 조건을 나눠 조사하고, 체험 후 실제 선택으로 다시 검증한다.

계산할 항목은 다음과 같다.

```text
사용자당 월 공헌이익
= 결제 후 실제 수취액
  - 이미지 분석·언어 모델 사용 비용
  - GPU 사용시간에 따른 전력·장비 또는 임대 비용
  - 저장·네트워크·처리 실패와 재시도 비용
  - 사용자당 지원·환불 등 변동 비용

손익분기 유료 사용자 수
= 월 고정 운영비 / 유료 사용자당 월 공헌이익
  (공헌이익이 양수일 때만 계산)
```

로컬 GPU 사용을 무료 원가로 계산하지 않는다. 동일한 월 요금이어도 착샷을 많이 생성하는 사용자에서 손실이 생길 수 있으므로 이용량·상한·대기열을 함께 검증한다. 광고·쇼핑 제휴는 초기 주 수익원으로 두지 않는다. ‘내 옷 재활용’ 가치와 구매 유도 사이의 충돌을 먼저 확인해야 한다.

### 11.5 차별성이 약할 때의 결정

이미지 재현이 높은 평가를 받아도 재사용이 낮으면 주간 구독보다 필요할 때 쓰는 이용권이 적합할 수 있다. 일정 입력 부담이 효용보다 크면 일정은 활동 두세 개를 선택하는 방식으로 단순화한다. 임베딩이나 언어 모델의 개선이 작으면 그 모델 호출을 줄이고 규칙 기반 경로를 유지한다.

경쟁 서비스보다 확실히 나은 과제가 확인되지 않으면 ‘대학생 전용’이라는 이름만으로 시장 우위를 주장하지 않는다. 가장 자주 해결된 문제와 사용자 집단으로 범위를 좁히고 다시 측정한다.

## 12. 구현 단계와 팀별 역할

### 12.1 단계별 완료 조건

4명이 기존 구조를 이해하고 함께 작업한다는 전제로 기능 통합까지 약 3~4주, 그 이후 최소 2주의 반복 사용 평가를 제안한다. 모델·데이터 품질과 팀 가용 시간에 따라 조정하며 평가 기간을 개발 기간에 포함해 축약하지 않는다.

| 단계 | 예상 작업 기간 | 산출물과 통과 조건 |
|---|---|---|
| 0 기준 확정 | 2~3일 | 경쟁 과제 비교표, 사용자 문제 인터뷰, 고정 평가 세트, 새 계약과 오류 정책 |
| 1 필수 의류 | 2~3일 | 선택 UI, 후보 고정, 전 경로 검증, PostgreSQL 소유권·충돌 회귀 통과 |
| 2 일정 추천 | 4~5일 | 수동 일정 카드, 착용 구간, 날씨 출처, 일정별 결과. 구조화 입력만으로 작동 |
| 3 사진 재현 | 5~7일 | 업로드·영역 확인, 태그 기준선·임베딩 비교, 파생 데이터 삭제 |
| 4 통합·최적화 | 3~4일 | 세 입력 조합, 캐시, GPU 공존, 모바일 E2E, 기존 API 회귀 |
| 5 사용자·사업 평가 | 최소 2주 | 블라인드 비교, 반복 사용·실제 착용, 원가·가격 가설 검증 |

실행 순서는 위와 같이 진행하되, 사진 재현의 품질 위험이 가장 크므로 B는 0단계부터 합성·허가 자료로 소규모 검색 실험을 병행한다. 복잡한 사진에서 신뢰할 결과가 나오지 않으면 본 구현 전에 입력 범위를 ‘한 인물이 선명하게 나온 사진’으로 제한한다.

### 12.2 담당별 변경

| 담당 | 주 작업 | 반드시 전달할 산출물 |
|---|---|---|
| A 추천 | 필수 후보 생성, 일정 점수, 참고 유사도와 조화 점수, 다양성, 규칙 대체 추천 | 버전 있는 점수 정책, 결정적 fixture, 비교 결과 |
| B 비전 | 참고 의류 영역·속성·임베딩, 불확실성, 의류 특징 재계산 | 특징 계약, 모델·전처리 버전, 실패 유형과 입력 조건 |
| C 백엔드 | JWT 소유권, 요청·응답 계약, 일정·참고 DB, 검증·트랜잭션, 삭제·제한·관측 | OpenAPI 예시, 마이그레이션, PostgreSQL 통합 테스트, 배포·복구 절차 |
| D 프론트 | 고정 옷, 일정 입력·확인, 사진 선택·자르기·분석 확인, 근거·착샷·행동 기록 | 모바일 전체 흐름, 오류 복구 UI, API 호환 테스트 |

공통 계약과 에러 예제를 먼저 합의한다. B가 DB에 직접 저장하거나 A가 사용자별 소유권을 추정하지 않도록 경계를 유지한다. C는 B의 특징과 A의 결과를 검증해 저장한다. D의 mock도 실제 계약과 같은 실패·제약 동작을 보여야 한다.

| 프론트 | `recommendation_ui.py`, `connect/recommendation.py` | 일정 편집·참고 사진 연결부 |
| 검증·문서 | 기존 추천·화면·마이그레이션 테스트 | 확장 통합·격리·동시성·품질 평가, 팀 계약 갱신 |

프로젝트에 이미 있는 미커밋 변경을 정리하거나 덮어쓰는 작업을 이 확장에 섞지 않는다. 구현 시 기능별로 변경을 나누고 기존 협업 문서의 PR 흐름을 따른다.

## 13. 검증 및 배포 계획

### 13.1 기능 검증

| 범위 | 필수 시나리오 |
|---|---|
| 필수 의류 | 1~3개 고정, 중복 슬롯, 제외 충돌, 세탁 중, 없는 ID, 다른 사용자 ID |
| 대체 추천 | timeout·잘못된 AI ID·빈 결과·DB 저장 전 상태 변경에도 조건 유지 |
| 일정 | 순서·중복 시간·자정·미확정 실내외·기온 없음·우선 일정·조건 충돌 |
| 참고 분석 | JPG·HEIC·회전·큰 이미지·다중 인물·잘린 옷·낮은 신뢰·지원 밖 카테고리 |
| 사진 검색 | 배경·포즈가 달라도 의류 비교, 색은 같지만 형태가 다른 경우, 부분 재현 |
| 통합 | 필수 옷과 참고 색 충돌, 일정과 참고 격식 충돌, 세 기능을 함께 사용 |
| 격리 | 다른 사용자의 일정·사진·추천·파일·분석 작업 조회·수정·삭제 차단 |
| 저장·삭제 | DB 커밋 실패, 파일 삭제 실패, 재시도, 탈퇴, 추천 문맥의 복사 정보 정리 |
| 동시성 | 여러 사용자의 업로드·추천·착샷, 동일 사용자의 중복 요청, 수정 중 추천 |
| 호환 | 기존 요청·과거 추천 조회·선호 스타일 순위·세탁·사진 삭제·소스 접근 차단 |

단위 테스트는 외부 모델을 고정 응답으로 대체해 제약을 재현한다. 실제 모델 평가는 별도 데이터 세트로 실행하고 지연·자원·실패를 기록한다. 모델을 대체한 테스트 통과를 실제 AI 품질 검증으로 보고하지 않는다.

### 13.2 실제 PostgreSQL 검증

운영·시연 DB와 분리된 실제 PostgreSQL 테스트 DB를 사용한다. 같은 서버를 이용하더라도 테스트 전용 DB 이름·사용자를 명시하고 생산 데이터에 seed·truncate·drop을 실행하지 않는다. 마이그레이션은 이전 revision의 예제 데이터를 넣은 테스트 DB에서 업그레이드와 과거 결과 조회를 검증한다.

모든 테스트는 `FITJANG_SKIP_DOTENV=1`과 명시적인 테스트 환경변수로 실행한다. `.env`를 직접 읽거나 `Settings()`, dotenv, 실행 스크립트, Docker Compose의 자동 로딩으로 읽지 않는다. 기존 계정·옷·사진의 개수와 식별자를 노출하지 않는 집계 및 필요 범위의 검증으로 보존 여부를 확인한다.

### 13.3 성능·화면 검증

성능은 작은 옷장과 큰 옷장을 나눠 측정한다. 예를 들어 의류 20·100·300개, 동시 사용자 1·5·10명, 캐시 유무, 착샷 진행 여부를 시험 조건으로 삼는다. 이 숫자를 현재 수용량으로 홍보하지 않는다.

초기 목표는 캐시된 특징으로 추천할 때 p95 3초 이내, 새 참고 사진의 분석 완료까지 p95 15초 이내로 제안한다. 실제 하드웨어에서 목표가 맞지 않으면 비동기 분석 상태와 예상 시간을 안내한다. 착샷 시간은 별도로 측정하고 이미 구현된 GPU 처리시간·대기열 추정을 유지한다.

로컬과 공개 HTTPS에서 동일한 기능 버전을 확인한다. 모바일에서는 사진 선택 → 자르기 → 특징 확인 → 필수 의류 고정 → 일정 입력 → 추천 → 선택적 착샷 → 삭제까지 검증한다. Android·iPhone 실기기 결과와 데스크톱 에뮬레이션 결과를 구분하고, 확보하지 못한 기기는 미검증으로 기록한다.

### 13.4 적용과 복구

1. 운영 전용 백업·복구 가능 여부를 확인하되 민감 내용을 출력하지 않는다.
2. 테스트 DB에서 마이그레이션과 데이터 보존을 검증한다.
3. 기존 서버와 호환되는 DB·백엔드부터 배포한다.
4. 새 기능을 별도 설정으로 꺼 둘 수 있게 하고 소규모 계정으로 확인한다.
5. 프론트 새 입력을 활성화해 로컬·멘토 서버에서 같은 결과를 확인한다.
6. 오류가 늘면 새 기능을 끄고 기존 추천을 유지한다. 데이터를 지우는 다운그레이드로 복구하지 않는다.

이미 승인된 운영 환경변수 전달 경로를 확인해 사용한다. `.env`를 읽는 시작 스크립트는 실행하지 않는다. 테스트 결과에는 실제 DB 사용 여부, 실제 모델 사용 여부, 외부 HTTPS 여부를 각각 명시한다.

## 14. 발표에서 보여 줄 검증 결과

발표는 기능 소개 후 바로 성능을 주장하기보다 아래 네 가지 증거로 구성한다.

| 질문 | 제시할 증거 |
|---|---|
| 누구에게 필요한가 | 대학생의 최근 실제 경험, 빈도, 현재 해결 비용과 반복 사용 |
| 기존 서비스와 무엇이 다른가 | 같은 옷·참고 스타일·복합 일정 과제의 완료 과정과 결과 비교 |
| AI를 왜 쓰는가 | 규칙 기준선 대비 사진 재현 품질·입력 시간 개선, 제거 실험 결과 |
| 지속 가능한 사업인가 | 실제 코디 선택·착용·재방문, 사용량별 비용, 유료 선택 결과 |

시연은 합성 인물과 허가된 참고 이미지로 수행한다. 예를 들어 남색 셔츠를 고정한 뒤 ‘밝은 상의와 어두운 하의’의 참고 사진, 실내 수업·발표·야외 이동 일정을 입력한다. 결과에서 셔츠가 유지되는지, 사진과 달라진 이유가 정확한지, 실내외 착용 안내가 적합한지 확인한다. 아우터를 고른 결과의 착샷은 안쪽 상의를 보존한 처리와 한계를 함께 보여 준다.

발표용 설명은 다음과 같이 시작할 수 있다.

> 저장한 스타일을 그대로 구매하는 대신, 이미 가진 옷과 오늘의 일정을 이용해 실제로 입을 수 있는 코디를 찾도록 돕습니다. 사용자가 고른 옷은 규칙으로 보장하고, AI는 사진과 자유로운 표현을 비교 가능한 스타일 정보로 바꾸는 데 사용합니다. 그 효과는 규칙 기반 추천과의 비교 및 실제 반복 사용으로 확인합니다.

‘최초’, ‘완벽한 재현’, ‘정확한 체형·핏 예측’, ‘AI 때문에 반드시 더 좋음’은 이 계획의 결론이 아니다. 구현 후 측정한 범위에서만 경쟁 우위와 AI 효과를 설명한다.
