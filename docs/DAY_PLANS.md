## 사용 흐름

1. **코디 추천 → 하루 일정 입력·관리**에서 날짜와 일정 카드를 입력한다.
2. 시작·종료, 목적, 실내/실외/혼합/모름, 활동 강도, 중요도를 확인한다. 최대 10개까지 가능하다.
3. 알고 있는 경우 구간의 최저·최고 기온을 함께 입력한다. 혼합 일정의 기온은 야외 구간 기준이다.
4. 저장하면 해당 일정이 추천 화면에서 선택된다. 필수 상의·하의·아우터와 선호 스타일을 함께 지정한다.
5. 아우터 기본값은 **계속 입기**다. **구간별로 벗고 소지 가능**을 직접 선택하면 실내에서는 벗거나,
   실외에서는 입는 안내를 허용한다. 벗는 구간에도 지정 아우터 ID는 코디에 유지된다.
6. 결과는 같은 상의·하의를 하루 동안 유지하는 최대 3개 코디다. 각 코디의 **하루 착용 안내**에
   시각·목적·실내외·아우터 상태·평가 근거가 나온다. 조건 바꾸기에서도 선택값을 유지한다.

착샷은 기존 전체 코디의 미리보기다. 각 일정의 아우터 상태별 착샷을 자동 생성하지 않는다.
오늘 기온/단일 상황 입력은 기존 요청 호환성을 위해 유지하며, 일정 추천에서는 저장된 구간 기온과
각 일정의 목적을 사용한다. 현재 기온을 저녁·미래 예보로 복사하지 않는다.

## 이번 입력과 판단의 범위

- IANA 시간대(기본 `Asia/Seoul`)와 UTC 오프셋이 있는 시작·종료 시각을 저장한다.
- 시간순으로 정렬하고 겹침, 역순, 1분 미만, 날짜 범위 초과, 잘못된 시간대를 거부한다.
  종료 시각 00:00은 다음 날짜 자정으로 처리하며, 자정을 넘겨 계속되는 일정은 날짜별로 나눈다.
- 목적은 수업·발표·면접·아르바이트·운동·약속·이동·기타다. 정확한 장소, 수업명, 약속 상대는 수집하지 않는다.
- 시간표 사진 인식, 캘린더 연동, 자연어 일정 생성, 자동 시간대별 예보는 포함하지 않는다.
- 실내 온도를 모르면 외부 온도나 임의의 실내 온도를 넣지 않는다. 기온/보온도가 없으면 보온 점수는
  계산하지 않고 정보 부족을 표시한다. 환경이 모름이면 입력 기온의 적용 환경도 확정하지 않는다.
- 혼합 일정은 야외 시간을 입력할 수 있다. 미입력 시 야외 비중 50%라는 임시 가정을 결과에 명시한다.
- 발표/면접은 부드러운 목적 선호다. 자동으로 정장을 필수로 만들지 않는다.
  사용자가 확인한 `required_style=formal|sporty`는 상·하의가 모두 해당 태그를 가져야 하는 조건이다.
  태그가 실제 행사 규정 준수를 보장하지 않으므로 확인 안내를 함께 표시한다.

## 추천과 대체 추천

필수 슬롯·사용 가능 상태·제외 의류를 먼저 적용한다. 조합은 순회하면서 상위 3개만 보관한다.
일정 경로에서는 기존의 ‘모든 의류를 현재 기온 하나로 개별 탈락’ 필터를 적용하지 않는다.

구간별 목적 적합성은 기존 상황 스타일 점수를 활용한다. 기온과 보온도를 모두 알 때만 조합 보온도를
비교하고 활동 강도에 따라 목표를 조정한다. 혼합 일정은 야외 시간 비중으로 보온 점수의 영향을 줄인다.
아우터가 탈착 가능하면 입은 상태와 벗은 상태를 비교한다. 이 계산은 경험적 초기 규칙이며
체감 온도, 실제 소재 보온성, 착용 만족도의 측정값이나 확률이 아니다.

- 구간 가중치: `clamp(시간 길이/60분, 0.25, 2) × 중요도(보통 1, 우선 2)`.
- 일정 점수: `0.6 × 구간 가중 평균 + 0.4 × 가장 낮은 구간 점수`.
- 최종 점수: `0.6 × 일정 점수 + 0.4 × 색상·선호 스타일 점수`.
- 지원되는 선호 스타일이 있으면 색상·선호를 반씩 반영하고, 없으면 색상 점수를 사용한다.
- 일정이 없으면 기존 색상·상황·선호 순위 계산을 그대로 사용한다.

local, mock 대체 추천, GPT 후보 생성은 같은 일정 조건을 사용한다. 서버는 결과를 다시 읽고
소유권·필수 의류·카테고리·확인된 복장 조건을 검증한 뒤 착용 안내를 재계산한다. 엔진이 만든
착용 상태나 점수 설명을 그대로 신뢰하지 않는다. 복장 조건을 만족하지 못하면 필수 옷을 바꾸거나
조건을 자동 해제하지 않고 `422 NO_FEASIBLE_OUTFIT`을 반환한다.

GPT6-Luna는 검증된 후보 ID의 **순서와 판단 이유**만 반환한다. 의류 구성·일정·착용 계획을 생성/수정하지
않는다. 일정의 목적·환경·길이·중요도·수동 기온과 후보 속성/규칙 판단을 전달하고, 사용자 ID,
일정 UUID, 실제 날짜·시각, 의류 UUID, 파일 경로와 사진은 전달하지 않는다. `store:false`와
엄격한 후보 집합 검증을 유지한다. 실제 외부 GPT 호출 대신 통제된 HTTP 정상/실패 응답으로
판단 계약을 검증했다. 후속 GPT 연결에서는 `.env` 외부의 암호화 키로 로컬·멘토 서버의 실제 판단을
활성화했다. 현재 설정과 실제 호출 검증은 [GPT 판단 연결 기록](REQUIRED_GARMENTS.md)을 참고한다.

## API 계약

| 경로 | 동작 |
|---|---|
| `POST /api/v1/day-plans` | 본인 일정 생성, 201 |
| `GET /api/v1/day-plans` | 본인 일정 목록, limit 1~100/offset |
| `GET /api/v1/day-plans/{id}` | 본인 일정 상세 |
| `PATCH /api/v1/day-plans/{id}` | 전체 확인된 입력과 `expected_version`으로 수정 |
| `DELETE /api/v1/day-plans/{id}?expected_version=1` | 일정과 추천 속 일정 사본 정리, 204 |

```json
{
  "date": "2026-11-12",
  "timezone": "Asia/Seoul",
  "events": [
    {
      "start_at": "2026-11-12T09:00:00+09:00",
      "end_at": "2026-11-12T10:00:00+09:00",
      "purpose": "presentation",
      "environment": "indoor",
      "priority": "high"
    },
    {
      "start_at": "2026-11-12T18:00:00+09:00",
      "end_at": "2026-11-12T19:00:00+09:00",
      "purpose": "travel",
      "environment": "outdoor",
      "temperature_min_c": 0,
      "temperature_max_c": 3
    }
  ]
}
```

추천은 기존 `POST /api/v1/recommendations`에 `schedule_id`, `schedule_version`,
`outerwear_policy`를 추가한다. ID/버전은 함께 보내야 한다. 일정 원문이나 점수를 직접 주입하는
`day_plan` 내용은 API가 거부한다. 공통 UserContext의 빈 `day_plan: null`만 호환용으로 허용한다.
응답 문맥에 검증된 일정 사본을 저장하고, 각 코디에
`wearing_plan`, `limitations`, `score_components`, `policy_version="day-plan-v1"`을 제공한다.

| 상황 | 응답 |
|---|---|
| 다른 사용자의 일정/없는 일정 | 동일한 404 `DAY_PLAN_NOT_FOUND` |
| 오래된 버전으로 수정·추천·삭제 | 409 `DAY_PLAN_CHANGED` |
| 추천 처리 중 일정 수정·삭제 | 저장 직전 재검증 후 409 `DAY_PLAN_CHANGED` |
| 시간 겹침·잘못된 기온·추가 필드 등 | 422 `VALIDATION_ERROR` |
| 확인된 복장 조건과 필수 옷 충돌 | 422 `NO_FEASIBLE_OUTFIT` |

JWT 사용자 범위에서 조회한다. 수정/삭제/추천 저장은 같은 일정 행을 잠가 버전 확인과 저장 사이의
경쟁을 방지한다. 기존 분당 10회 추천 제한, 결과 조회 격리와 피드백 API도 유지한다.

## 저장·삭제와 마이그레이션

0017은 `day_plans` 테이블과 `recommendation_outfits.details` JSONB 열만 추가한다.
기존 열/행/계정/이미지를 변경하지 않는다. 최대 10개 이벤트는 계획서의 별도 이벤트 테이블 대신
일정 행의 검증된 JSON 배열로 묶어 한 버전으로 원자적으로 수정한다. 날짜·사용자·버전은 일반 열이다.
과거 추천의 details 기본값은 `{}`이고, 일정이 없던 문맥은 선택 필드의 기본값으로 조회한다.

일정 삭제 시 과거 추천의 일정 ID·버전·사본을 비우고, 구간 설명·GPT 사유·일정 점수를 정리한다.
코디의 의류 ID와 피드백은 유지한다. 계정 탈퇴 시 일정은 사용자 FK cascade로 삭제된다.
테스트는 기존 서비스 스키마와 분리한 임시 PostgreSQL 스키마 및 합성 의류 이미지로만 수행한다.
`.env`는 열지 않으며 테스트/시연 경로는 `FITJANG_SKIP_DOTENV=1`과 접근 차단 audit hook을 사용한다.

## 검증

- 실제 PostgreSQL에 모든 Alembic 적용, ORM 일치 및 이전 데이터 보존.
- 일정 생성·조회·수정·삭제, 소유권, 버전 충돌, 탈퇴 cascade, 과거 추천 사본 삭제.
- 발표/운동 목적에 따른 순위 차이, 일정 시간 길이·중요도 반영, 실내 온도 미확정 처리.
- 필수 의류 유지와 엔진 예외·시간 초과·잘못된 결과·GPT 오류의 대체 추천.
- 두 사용자의 실제 HTTP 동시 요청 격리, 동시 일정 수정의 한 건 성공/한 건 409.
- 실제 브라우저에서 두 일정 생성 → 저장 → 필수 상의/아우터 → 탈착 설정 → 추천 → 조건 복원.
- 모바일 폭으로 레이아웃 확인. Android/iPhone 실기기 검증과 외부 GPT 품질 측정은 수행하지 않았다.

주요 테스트: `backend/tests/api/test_day_plans.py`, `backend/tests/test_day_schedule.py`,
`backend/tests/e2e/test_day_plans.py`. 화면 증빙과 XML 결과는 Git 제외 경로 `.demo/day-plans-ui/`에 둔다.

### 실행 결과와 반영

- 추천·일정·마이그레이션·프론트·피드백·요청 제한·공개 경계 통합/회귀 세트: **237건 통과**.
- 추가 팀 계약/공통 UserContext 호환성 세트: **32건 통과, 1건 건너뜀**.
  별도 D 팀원 체크아웃 경로 `TEAM_FRONTEND_ROOT`가 필요한 항목만 건너뛰었으며,
  현재 통합된 프론트는 실제 TCP·PostgreSQL·브라우저로 검증했다.
- 자정 종료 재수정 및 직렬화 호환성 최종 확인: **2건 통과**.
