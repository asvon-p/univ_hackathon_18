# 개인 옷장과 테스트용 옷장

- `/wardrobe?wardrobe=personal`: 직접 등록한 의류만 표시합니다.
- `/wardrobe?wardrobe=example`: 계정별 예시 의류만 표시합니다. 신규 제공은 아우터·상의·하의 각 3벌입니다.
- 기존 `is_example=true` 의류는 ID·속성·사진을 그대로 유지하면서 테스트용 화면에 표시합니다. 사용자가 수정·삭제한 예시는 복구하거나 덮어쓰지 않습니다.
- 예시를 받지 않은 기존 계정은 명시적인 보충 작업으로 9벌을 받습니다. 가입 시에는 기존 가입 트랜잭션에서 제공합니다.
- `starter_wardrobe_provisioned` 기록으로 중복 제공과 삭제한 예시의 자동 재생성을 방지합니다. 개별 사용자 행 잠금으로 동시 보충도 직렬화합니다.
- 파일/DB 실패 시 새로 만든 의류 파일만 정리하며, 정리 실패는 기존 삭제 작업 큐로 재시도합니다. 커밋 후 응답 유실 시 살아 있는 파일은 보존합니다.

## 추천과 API

`GET /api/v1/garments`, `GET /api/v1/garments/page`, 추천 생성 요청의 `wardrobe`는 `personal`, `example`, `all`을 지원합니다. 기존 클라이언트와 저장 결과를 위해 API 기본값은 `all`입니다.

실제 UI는 개인 옷과 예시 옷을 분리해서 선택합니다. 추천 화면에 처음 진입하면 직접 등록한 옷이 있는 계정은 개인 옷장을, 없는 계정은 테스트용 옷장을 선택합니다. 옷장 변경 시 필수·제외 의류만 초기화하고 기온·스타일·일정·참고 스타일은 유지합니다.

서버는 선택한 옷장의 전체 의류를 후보로 사용하고, GPT 판단·local 추천·대체 추천 및 저장 직전 재검증까지 같은 범위를 적용합니다. 다른 옷장의 의류를 필수 선택으로 끼워 넣을 수 없습니다. 목록 검색·개수·페이지 커서에도 옷장 범위를 적용합니다. 관리자도 일반 의류 API에서는 본인 의류에만 접근합니다.

기존 추천 기록은 변경하지 않습니다. 이전 추천은 `all` 범위로 읽히며, 이전 요청 키의 중복 처리 방지도 유지됩니다. 홈은 개인 옷이 있으면 개인 옷장, 없으면 테스트용 옷장의 저장된 추천과 개수를 표시합니다.

## 피드백 분리

- 좋아요·별로예요는 해당 추천이 생성된 옷장에만 반영됩니다. 개인 옷장과 테스트용 옷장은 양방향으로 분리합니다.
- 서버가 저장된 추천의 `context.wardrobe`를 사용합니다. 피드백 요청에 임의의 옷장이나 사용자 정보를 넣어서 반영 범위를 바꿀 수 없습니다.
- 같은 옷장의 최신 의견을 코디별로 선택한 뒤 최근 20건을 사용합니다. 다른 옷장의 의견이 많아도 이 20건을 밀어내지 않습니다.
- GPT에 전달하는 의견·local 점수 조정·대체 추천 모두 동일한 필터를 통과합니다. 기존 순위·결과는 그대로 두고 새로 생성하는 추천부터 적용합니다.
- 옷장 구분이 없거나 `all`인 이전 추천은 전체 옷장 범위에서만 사용합니다. 개인/테스트 옷장에 추정 배정하지 않습니다. 유효하지 않은 옷장 값, 삭제·익명화된 추천의 피드백은 새 개인/테스트 추천에 전달하지 않습니다.
- 기존 피드백과 추천 기록을 수정·삭제하지 않으며 추가 DB 마이그레이션은 필요하지 않습니다.

### 피드백 분리 검증 (2026-11-16)

- 실제 PostgreSQL 임시 스키마에서 관련 API·HTTP E2E 회귀 테스트 65개 통과. 개인→테스트 및 테스트→개인 양방향 분리, 순위·점수 불변, 같은 옷장 순위 변경, 최신 의견 우선, 20건 제한, 과거 기록 보존, 사용자 접근 차단을 확인했습니다.
- OpenAI 전송 요청을 테스트 transport로 검사하여 다른 옷장 의견이 전달되지 않음을 확인했습니다. API 오류 시 local 대체 추천도 같은 기준을 적용합니다. 이 검증에는 유료 GPT 호출을 사용하지 않았습니다.
- 별도 PostgreSQL 검증 계정으로 실제 브라우저에서 좋아요·별로예요 입력, 상세 의견 저장, 새로고침 후 선택 상태, 옷장 변경 및 새 추천을 확인했습니다. 테스트용 의견 2건은 다음 테스트 추천에만 포함되고 개인 추천에는 0건이 포함됐습니다. 검증 서버·스키마는 종료 후 정리했습니다.
- 로컬·멘토 서버를 재시작했고 공개 HTTPS 로그인 200, 소스 경로 차단 404를 확인했습니다. 기존 GPT/GPU 연결과 공유 DB를 유지했습니다.
- 운영 계정 35개, 의류 368벌, 추천 108건, 피드백 38건과 파일 820개의 기존 행·파일 해시가 유지됐습니다. `.env` 접근 없이 진행했습니다.

## 착샷 요청 분리 (2026-11-16)

- `POST /api/v1/tryon-results`는 한 요청에 내 옷장과 테스트용 옷장의 의류를 섞을 수 없습니다. 로그인 사용자의 의류 소유권·착용 역할을 먼저 검증하고, DB의 `is_example`으로 같은 옷장인지 확인합니다.
- 요청의 선택적 `wardrobe` 값은 `personal` 또는 `example`입니다. 생략한 이전 클라이언트도 실제 의류를 기준으로 검증합니다. `all`은 착샷 접수에서 허용하지 않습니다.
- 혼합 의류는 `422 TRYON_WARDROBE_MIXED`, 선언한 옷장과 실제 의류가 다르면 `422 TRYON_WARDROBE_MISMATCH`로 거절합니다. 다른 사용자의 의류·잘못된 착용 역할은 기존처럼 `404`입니다. 거절된 요청은 착샷 결과 행이나 대기열 예약을 만들지 않습니다.
- 프론트 `/tryon`도 같은 검증을 수행하고 서버로 확인한 옷장 값을 전달합니다. 이미지가 없어 GPU 단계에서 제외될 의류도 검사합니다. 기존 결과·진행 중 캐시를 반환하기 전에 검사하므로 캐시로 검증을 건너뛸 수 없습니다.
- 코디 카드에는 `내 옷장의 의류만 입혀요` 또는 `테스트용 옷장의 의류만 입혀요`를 표시합니다. 이전에 저장된 혼합 코디는 새 착샷 버튼 대신 안내와 옷장 재선택 링크를 표시합니다.
- 기존 착샷 기록·이미지·계정은 변경하거나 삭제하지 않습니다. 과거 혼합 착샷도 이력에서 소유자가 조회할 수 있지만 새 혼합 요청은 거절합니다. 추가 DB 마이그레이션은 필요하지 않습니다.
- 실제 PostgreSQL 격리 스키마의 API 회귀 검사와 프론트 단위 검사 70개, 로컬·멘토 HTTP E2E 6개가 통과했습니다. 영구/세션 사진 정책, 생략·위조한 옷장 값, 타 사용자 접근, 잘못된 착용 역할, 캐시·사진 생략 경로, 정상 저장·재조회·중복 재사용을 확인했습니다.
- 실제 브라우저에서 두 옷장의 안내, 각각의 착샷 요청·완료·결과 표시 및 혼합 코디 차단을 확인했습니다. 테스트에서는 별도 계정·PostgreSQL 스키마·합성 시험 이미지를 사용했고 GPU 추론 경계만 테스트 응답으로 대체했습니다. 사용자의 사진은 사용하지 않았습니다.
- 로컬·멘토 앱을 재시작했고 두 API·두 프론트 및 고정 공개 HTTPS에서 혼합 요청의 `422` 거절을 확인했습니다. 기존 GPU 연결·자동 실행·소스 경로 `404` 차단을 유지했습니다. 운영 계정 35개, 의류 368벌, 추천 111건, 피드백 38건, 착샷 10건 및 이미지 파일 828개의 기존 행·파일 해시를 확인했습니다. `.env`는 읽거나 수정하지 않았습니다.

## 운영 명령

`.env`를 열지 않는 기존 실행기로 Alembic `0026`을 먼저 적용합니다. 기존 서버와 계정·이미지를 공유하는 유지보수 명령입니다.

```powershell
$env:FITJANG_SKIP_DOTENV = '1'
& 'C:/Users/user/miniconda3/envs/univ18/python.exe' -m scripts.provision_test_wardrobes
& 'C:/Users/user/miniconda3/envs/univ18/python.exe' -m scripts.provision_test_wardrobes --apply
```

첫 명령은 대상 수만 확인합니다. 두 번째 명령은 아직 제공 기록이 없는 계정만 보충합니다. 로그인·재시작에서는 보충하지 않습니다. 데이터베이스와 이미지 경로가 다른 배포에는 이 로컬 전용 명령을 사용하지 않습니다.
