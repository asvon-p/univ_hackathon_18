# 착용 역할과 옷 형태 분리

2026-11-13 구현. 기존 의류 ID·속성·사진과 추천 기록은 유지한다.

## 사용 방법

1. 옷 등록에서 **착용 역할**을 선택한다. 티셔츠 위에 걸칠 셔츠는 **아우터**로 고른다. 모르면 **분석 후 선택**으로 둔다.
2. 사진 분석 다음 화면에서 **옷 형태**를 별도로 확인한다. **아우터 + 셔츠**, **아우터 + 가디건**, **상의 + 셔츠** 등을 저장할 수 있다.
3. 기존 의류는 **정보 수정**에서 역할과 형태를 각각 바꾼다. 역할을 변경해도 형태 선택은 사라지지 않는다.

사진 자르기 비율(일반 1:1, 긴 옷 2:3)은 역할·형태와 별개의 선택이다.

## 데이터 및 호환성

| 의미 | 명시적인 API 필드 | 기존 API·DB 필드 | 예시 |
|---|---|---|---|
| 코디에서의 착용 역할 | `wearing_role` | `category` | `outerwear` |
| 옷의 형태 | `garment_type` | `subcategory` | `shirt` |

DB에 이미 독립된 두 컬럼이 있으므로 새 컬럼이나 데이터 재분류 마이그레이션은 필요하지 않다. 값이 중복 저장되지 않으며 조회 응답은 새 이름과 기존 이름을 모두 제공한다. 역할은 추천에서 `top`, `bottom`, `outerwear`를 사용한다. 기존 `shoes` 데이터의 조회·수정 호환성은 유지하지만 추천·착샷에는 포함하지 않는다.

`POST /api/v1/garments` multipart의 선택 항목:

- `wearing_role=outerwear`: 최초 분석 전에 사용자가 정한 역할 저장.
- `garment_type=shirt`: API에서 형태까지 지정할 경우 분석 전에 보호.
- 생략하면 비전의 추정 결과 사용. 프론트는 역할만 미리 전달하고 형태는 분석 후 확인한다.

`PATCH /api/v1/garments/{id}` 예시:

```json
{"wearing_role": "outerwear", "garment_type": "shirt"}
```

기존 `category`·`subcategory` PATCH도 지원한다. 한 요청에서 동일 의미의 새 이름과 기존 이름을 동시에 보내면 모호한 변경을 막기 위해 422로 거절한다. 역할에 `shirt` 같은 형태 값을 넣거나 null로 지우는 요청도 거절한다. 형태는 기존 계약처럼 최대 50자 문자열이며, 기존 모델의 사용자 정의 형태를 수정 화면에서 유실하지 않는다.

## 자동 분석·재분석

선택한 역할은 기존 `user_edited_fields`의 `category`로, 선택한 형태는 `subcategory`로 저장한다. 첫 분석·재분석은 사용자가 선택한 필드를 덮어쓰지 않는다. 역할만 선택한 경우 형태·색상 등 미수정 필드는 계속 분석할 수 있다. 분석 실패 시에도 선택한 역할을 유지한다. `role_source=user|model|null`로 역할 결정 출처를 조회한다.

확인 화면에서 저장하면 사용자가 확인한 속성이 보호된다. 이미 수동 수정한 기존 의류에도 동일한 보호 규칙이 적용된다. 기존 자동 분석 결과는 임의로 재분류하지 않는다.

## 추천 및 착샷

- local 추천 후보 분류·필수 의류 조건·fallback·결과 검증은 착용 역할을 기준으로 한다. `outerwear + shirt`는 상의 슬롯을 대체하지 않는다.
- GPT는 서버가 만든 후보의 순위와 이유만 판단한다. 지시에 역할/형태의 차이를 명시했으며 후보의 의류·슬롯을 바꿀 수 없다.
- 착샷은 **하의 → 상의 → 아우터** 순서로 진행한다. 아우터 역할의 셔츠도 상의 적용 결과를 입력받고 기존 안쪽 상의 보존 처리를 사용한다.
- DB는 소유자와 슬롯 역할을 확인한다. 다른 사용자의 의류, 아우터를 상의 슬롯에 넣는 요청은 거절한다.
- 역할을 변경하면 과거 착샷 기록은 보존하되 새 조건의 결과로 재사용하지 않는다.

역할을 선택하는 것과 앞이 열린 사진을 확보하는 것은 별개다. 단추를 잠근 사진에서 보이지 않는 안쪽을 정확히 복원하는 기능은 아니다. 기존 자동 안쪽 탐지·수정 및 불확실성 안내를 유지한다.

## 검증

실제 PostgreSQL 독립 스키마에서 최초 분석·재분석 실패/성공, 역할/형태 별도 변경, 기존 API 호환, 사용자 접근 차단, local/fallback 추천, 착샷 슬롯과 기록 보존을 검증한다. 로컬·멘토 UI HTTP E2E는 실제 서버와 PostgreSQL을 사용한다. GPU/브라우저 검증은 임시 계정 및 기존 합성 인물·생성 의류로만 수행하며 완료 후 임시 계정을 삭제한다.

테스트 명령 예시(PowerShell):

```powershell
$env:FITJANG_SKIP_DOTENV = '1'
$env:TEST_POSTGRES = '1'
$env:TEST_DATABASE_URL = 'postgresql+psycopg://fitjang:fitjang@127.0.0.1:5432/fitjang_test'
python -m pytest backend/tests/api/test_wearing_roles.py backend/tests/e2e/test_wearing_roles.py backend/tests/test_tryon_frontend.py
```

운영 `.env`는 읽거나 수정하지 않는다. 검증 증적은 git에서 제외된 `.demo/wearing-roles/`에 기록한다.

### 실제 검증 결과 (2026-11-13)

- PostgreSQL 통합을 포함한 관련 회귀 191개 및 공통 계약·MVP E2E 7개, 총 198개 통과.
- 로컬 화면에서 생성한 셔츠 사진을 아우터로 업로드하고, 상의/아우터 역할을 바꿔도 형태 선택이 유지되는 것을 확인했다. 저장 및 실제 비전 재분석 후에도 `outerwear + shirt`가 유지됐다.
- 공개 HTTPS 화면의 필수 아우터 선택 및 GPT 추천 이유에서 셔츠의 겉옷 역할을 확인했다. 합성 인물로 GPU 착샷을 생성하고 로컬·멘토 양쪽에서 같은 결과를 조회했다.
- 검증 사진은 단추를 잠근 셔츠여서 기존 아우터 처리의 `approximate` 결과와 앞여밈 추정 안내가 표시됐다. 안쪽 니트는 보존됐지만 정확한 열린 셔츠 모양을 검증한 것은 아니다.
- 임시 계정을 삭제한 후 기존 계정 6개, 의류 39벌, 추천 68건, 기존 착샷 1건, 이미지 파일 112개의 기존 행/파일이 그대로 보존됐다. 실제 GPT 검증 호출 1건의 사용량 기록만 추가됐다.
- 로컬 UI 3000, 멘토 UI 3001, 공개 HTTPS 8443, GPU 8010 정상 가동. `.env` 직접·간접 접근 없이 실행했다.
