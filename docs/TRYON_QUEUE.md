# 착샷 접수 제한과 사용자별 대기열

## 적용 정책

- 로그인한 사용자 ID별로 실행·대기 중 코디는 **1개**입니다. 새 로그인, 다른 탭,
  로컬/멘토 주소를 이용해도 동일한 제한을 받습니다.
- 두 서버를 합쳐 **8개 코디**까지 접수합니다. 실행 중인 코디도 포함하며,
  상의·하의·아우터를 모두 선택해도 한 코디로 셉니다.
- PostgreSQL `tryon_queue_state`의 단일 행 잠금과 `tryon_admissions.user_id`의
  고유 제약으로 동시 접수 경쟁을 제어합니다. 기본 capacity는 8이며 DB 제약상 1~8입니다.
  현재 GPU 설정에서 값을 임의로 늘리지 않습니다.
- GPU worker는 1개입니다. 준비된 사용자 사이에서 의류 한 벌씩 순환하고,
  사용자 내부에서는 하의 → 상의 → 아우터 순서를 유지합니다.
  다른 사용자의 다음 의류가 아직 도착하지 않았으면 준비된 작업을 처리합니다.
  GPU를 사용자마다 분할하거나 동시에 여러 모델 추론을 실행하지 않습니다.

## API와 화면

| 요청 | 동작 |
| --- | --- |
| `POST /api/v1/tryon-results` | 소유 의류·사진 검증 후 접수 자리를 원자적으로 예약 |
| `POST /api/v1/tryon-results/{id}/heartbeat` | 본인 작업의 접수 유효기간 갱신, 204 |
| `POST /api/v1/tryon-results/{id}/cancel` | 본인 작업의 접수 자리 반환, 204 |
| `PUT /api/v1/tryon-results/{id}/image` | 유효한 접수만 결과 확정 후 자리 반환 |
| 프론트 `POST /tryon/{id}/cancel` | 백엔드 예약 취소 및 프론트 작업/GPU 대기 작업 정리 |

진행 중 작업이 이미 있으면 `429 TRYON_USER_BUSY`와 `Retry-After: 5`,
전체 접수가 차면 `429 TRYON_QUEUE_FULL`과 `Retry-After: 10`을 반환합니다.
새 요청을 자동으로 무한 재접수하지 않으며 화면에 재시도 안내를 표시합니다.
같은 화면에서 같은 코디를 다시 요청하면 기존 작업을 돌려주는 동작은 유지합니다.
화면에는 대기 순서와 생성 취소 버튼을 표시합니다.

GPU 내부 API는 별도 키로 보호되며, 프론트가 검증된 사용자 ID와 단계별 요청 ID를 전달합니다.
같은 단계의 통신 재시도는 기존 GPU 작업으로 합쳐 중복 추론을 방지합니다.
클라이언트가 제공한 사용자 ID를 그대로 신뢰하지 않습니다.

## 실패·취소·재시작

- 완료, 실패, 취소, 사진 교체·삭제, 동의 철회, 계정 탈퇴 시 접수 자리를 반환합니다.
  고객 세션의 로그아웃·만료도 자리를 반환합니다.
- 프론트는 진행 중 heartbeat를 보냅니다. 마지막 갱신 후 **120초**가 지나면
  예약이 만료되며, 새 접수 또는 주기적 정리에서 회수합니다.
- 작업당 최대 예약 시간은 **15분**이며 heartbeat로 무한 연장할 수 없습니다.
  만료/취소된 작업의 늦은 결과 업로드는 `409 TRYON_EXPIRED`로 거절합니다.
- GPU 대기 중 취소는 대기열에서 즉시 제거됩니다. 이미 실행 중인 CUDA 추론은
  현재 한 단계가 끝날 때까지 실행될 수 있지만 그 결과는 게시하지 않습니다.
- 서버 재시작은 진행 중 GPU 작업을 복구하지 않습니다. 남은 예약은 만료되며
  사용자가 다시 요청해야 합니다. 기존 영구 저장 결과·옷장·계정은 유지합니다.

## 데이터와 운영

마이그레이션 `0014`는 접수 상태 테이블 두 개만 추가합니다. 기존 레코드를 변환하거나
이미지를 옮기지 않습니다. 고객 사진·착샷은 기존 세션 RAM 정책을 유지합니다.
DB에 추가되는 정보는 사용자·작업 ID, 세션 해시, 만료 시각 등 임시 접수 정보이며
사진이나 코디 내용은 포함하지 않습니다.

8개는 접수 상한이며 8명 동시 추론 성능 보장이 아닙니다. 실제 처리 시간은
의류 수·모델·GPU 부하·네트워크에 따라 달라집니다. 현재 화면은 실제 GPU 처리 기록과
순환 대기열로 예상 범위를 표시합니다. [예상 시간 계산과 검증](TRYON_ETA_AND_LAYERING.md)을 참고하세요.

테스트는 `FITJANG_SKIP_DOTENV=1`, `TEST_POSTGRES=1`과 명시적 테스트 DB를 사용합니다.
실제 PostgreSQL 격리 스키마에서 사용자별/전역 동시 접수, 만료, 취소, 소유권,
로그아웃, DB 커밋 실패 및 모델/마이그레이션 일치를 검증합니다.

관련 코드: `backend/app/services/tryon_admission.py`,
`backend/app/services/tryon_results.py`, `tryon_server/fair_queue.py`,
`tryon_server/server.py`, `frontend/avatar_preview.py`.

## 2026-11-11 적용 검증

- 실제 PostgreSQL 전체 회귀 487개 통과, 외부 입력이 필요한 2개 제외.
  이후 기본 상한 8개·동의 철회 사례를 확장한 접수 테스트 13개도 통과했습니다.
- 모델을 실행하지 않는 GPU HTTP 회귀 2개에서 단계별 재시도 중복 방지,
  취소 후 대기 슬롯 반환, 내부 키 보호, 10개 동시 요청 중 8개 접수를 확인했습니다.
- 동일 사용자의 6개 동시 요청은 1개만 접수, 나머지 5개는 429입니다.
  서로 다른 9명의 동시 요청은 8개 접수, 1개 `TRYON_QUEUE_FULL`로 거절됐습니다.
- 로컬/멘토 프론트를 나누어 임시 고객 계정 3개가 상의·하의를 각각 요청했습니다.
  실제 RTX 5090 처리 순서는 **A 하의 → B 하의 → C 하의 → A 상의 → B 상의 → C 상의**였습니다.
  요청 시작부터 각 코디 완료까지 35.547초, 44.125초, 51.922초가 걸렸습니다.
  한 번의 합성 사진 실측이며 일반 사용자 지연 시간 보장이나 p95 측정은 아닙니다.
- 같은 사용자가 다른 백엔드로 접수해도 429, 다른 사용자의 결과 조회·취소는 404입니다.
  생성 취소 후 DB 예약이 제거되고 고객 사진·결과가 DB/파일에 남지 않음을 확인했습니다.
- 공개 DNS → Funnel HTTPS 경로에서 완성 이미지 200과 `private, no-store`를 확인했습니다.
- 운영 스키마는 `0013 → 0014`, Alembic/ORM 차이는 없습니다. 로컬·멘토·GPU와
  로그인 후 자동 실행 감독이 모두 정상 상태입니다.
- 기존 계정 7개, 의류 45개, 저장 착샷 3개를 포함한 모든 기존 업무 레코드의 해시,
  이미지 파일 117개와 자격 파일 4개의 해시가 유지됐습니다. 검증 중 추가된 실제 추천도 보존했습니다.
  검증을 위해 만든 임시 계정 3개와 해당 의류만 삭제했습니다. `.env` 접근은 차단했습니다.
- 검증 기록은 Git 제외 경로 `.demo/tryon-queue/`에 있습니다. 새 코드 외 기존 작업은 유지했습니다.
