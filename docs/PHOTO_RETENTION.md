# 사진 보관 정책과 고객 검증 계정

로컬·멘토 서버는 PostgreSQL과 이미지 저장소를 공유한다. 마이그레이션 `0016`부터
기존 계정과 새로 가입하는 계정 모두 전신 사진을 보관할 수 있다. 업로드할 때 보관과 착샷 활용에
동의해야 한다. 기존 임시 세션의 사진은 복사하지 않는다. 임시 저장 정책을 사용하던 계정은
다시 로그인한 뒤 저장할 사진을 올린다.

프로필의 **사진·착샷 삭제**는 전신 사진, 버전 정보, 착샷 결과 파일과 기록을 모두 정리한다.
계정·옷장·추천·피드백은 유지한다. 삭제는 먼저 조회를 차단한 뒤 파일을 즉시 제거한다.
파일 삭제가 실패하면 정리 중으로 표시하고 서버가 다시 시도한다.
사용자가 다운로드한 사본은 사용자가 직접 지운다.

삭제 요청을 받은 운영자는 공유 저장소를 사용하는 PC에서 아래 명령으로 대상을 확인한 뒤
`--apply`를 추가해 삭제할 수 있다. 기본 실행은 사진을 열지 않고 저장 여부와 정리 대상 건수만 조회한다.

```powershell
$env:FITJANG_SKIP_DOTENV = "1"
python -m scripts.purge_body_photo --email "요청자 이메일"
python -m scripts.purge_body_photo --email "요청자 이메일" --apply
```

## 이전 세션 보관 정책

아래는 마이그레이션 `0016` 이전 시연 정책과 `session`을 명시한 별도 환경에 해당한다.
사진 보관 방식은 `users.photo_policy`로 구분한다.

| 데이터 | 기존 멘토·로컬·QA (`persistent`) | 고객 검증·새 가입 (`session`) |
| --- | --- | --- |
| 계정·프로필·의류·추천·피드백 | DB에 유지 | DB에 유지 |
| 전신 사진 | 기존 방식대로 개인별 파일 보관 | 로그인 세션의 메모리에서만 처리 |
| 완성된 착샷 | `tryon_results` 메타데이터 + 개인별 JPEG 파일 | 로그인 세션의 메모리에서만 처리 |
| 로그아웃 | 보관한 사진 유지 | 해당 세션 사진·착샷 삭제, JWT 사용 차단 |
| 30분 미사용 | 기존 JWT 만료 정책 | 해당 세션 종료 및 사진·착샷 삭제 |
| 서버 종료·재부팅 | 완료된 착샷 유지 | 메모리 사진·착샷 소멸, 다시 업로드 필요 |

`customer-validation@example.com`은 session 정책이다. 기존 멘토·로컬·QA 계정의
ID·비밀번호·옷장은 바꾸지 않았다. 두 시연 실행기는 새 가입에 `NEW_USER_PHOTO_POLICY=session`을
명시한다. 일반 백엔드 설정의 기본값은 `persistent`이며, 설정 변경은 **새 계정에만** 적용된다.
기존 계정의 정책은 DB 값을 별도로 전환해야 한다. persistent→session 전환 시 기존 저장 사진도
먼저 정상 삭제 절차로 정리해야 한다. 단순히 정책 컬럼만 변경하면 기존 파일이 없어지지 않는다.

## 이용 흐름

1. 로그인한 뒤 전신 사진 활용에 동의하고 업로드한다.
2. 본인의 옷장 의류만 선택하여 착샷 생성을 요청한다.
3. GPU가 하의 → 상의 → 아우터 순으로 생성한다. 프론트는 매 단계 결과를 받은 뒤 GPU 작업을 삭제한다.
4. persistent 계정은 최종 JPEG를 백엔드 파일 저장소에 넣고 DB에 소유자·의류 구성·사진 버전을 기록한다.
   session 계정은 백엔드 메모리에만 둔다. 사진 바이트·사진 경로·착샷 레코드를 DB에 남기지 않는다.
5. **내 착샷**(`/tryon/history`)에서 완성된 결과를 조회하거나 삭제한다. persistent 계정은 재로그인·재시작 후에도 조회된다.

원본 전신 사진만 삭제해도 persistent 계정의 이미 완성된 착샷은 별도 보관된다.
완성 결과도 없애려면 내 착샷에서 삭제한다. 신체정보 동의를 철회하거나 탈퇴하면 관련 보관 결과도 정리한다.
생성 도중 서버를 끄면 해당 작업은 자동 재개하지 않는다. 중단된 요청은 다시 생성한다.

## 고객 사진 삭제 시점

- 로그아웃: 서버가 세션을 폐기하고 이미지 메모리 참조를 제거한다. 같은 JWT로 다시 접근해도 401이다.
- 미사용: 페이지 진입과 클릭·키 입력·스크롤 등 사용자 활동을 서버에 기록한다(분당 최대 한 번).
  마지막으로 기록된 활동부터 30분이 지나면 접근을 차단한다. 상태 폴링만으로 시간을 연장하지 않는다.
- 정리 작업은 기본 30초 간격으로 만료·취소 세션을 확인한다. 다른 백엔드 프로세스의 메모리도
  다음 정리 주기에 폐기한다. 프로세스 재시작은 메모리를 없애며 DB에 이미지가 없어 복원되지 않는다.
- 브라우저를 닫는 순간은 감지에 의존하지 않는다. 로그아웃하지 않고 닫으면 위 미사용 만료를 적용한다.
- GPU 계산 중 로그아웃하면 프론트가 인증 만료를 감지하여 작업을 폐기한다. 이미 실행 중인 CUDA 연산은
  현재 단계가 끝나야 입력을 해제할 수 있다. 완료 결과는 게시하지 않는다. 프론트가 비정상 종료되어도
  GPU의 미수거 임시 결과는 완료 후 60초 + 최대 15초 정리 주기 안에 제거한다.

신규 GPU 요청은 `ephemeral=true`로 전송되어 중간·최종 결과를 GPU outputs 폴더에 기록하지 않는다.
세 서버의 multipart 파서는 요청 크기를 제한하면서 임시 업로드가 디스크로 넘어가지 않도록 한다.
DB의 `media_sessions`에는 인증 토큰 해시·사용자 ID·만료 시각만 저장한다.
응답은 `private, no-store`이며 이미지별 소유자를 검사한다. 다운로드한 파일·스크린샷 등 사용자가
직접 보관한 사본은 서버에서 지울 수 없다. 메모리 참조 제거가 OS 스왑·크래시 덤프까지 덮어쓰는 기능은 아니다.

현재 MVP는 각 백엔드당 단일 프로세스로 운영한다. session 사진 메모리는 로컬 백엔드와 멘토 백엔드
사이에 공유하지 않는다. 고객 검증 중에는 공개 HTTPS 주소를 계속 사용한다. 옷장과 추천 이력은 어느
주소에서도 같은 계정으로 조회할 수 있다. 여러 worker로 확장하려면 임시 이미지의 분산 수명 관리가 필요하다.

## 참여자별 계정 분리

**참여자 한 명당 계정 하나**를 사용한다. 예를 들어 P001, P002를 서로 다른 로그인 계정에 대응시키고,
각자 다른 비밀번호를 제공한다. 실제 이메일을 받을 필요가 없는 수동 발급은 참여자 번호를 쓰되
로그인 ID는 API의 이메일 형식을 만족시킨다. 관리자가 가지고 있는 번호 대응표는 공개하지 않는다.

- 같은 계정을 여러 사람이 사용하면 옷장·선호 스타일·추천·피드백이 같은 `user_id`에 쌓인다.
- 시크릿 창, 다른 브라우저, 다른 로그인 토큰만으로는 위 데이터가 분리되지 않는다.
- 별도 계정이면 옷·추천·피드백은 소유자별로 차단된다. 사진은 추가로 로그인 세션별로 분리된다.
- 한 참여자는 후속 테스트에서도 같은 계정을 사용하면 이전 옷장과 피드백을 이어서 활용할 수 있다.
- 계정 분리는 GPU 자원까지 나누지는 않는다. GPU는 하나의 대기열을 사용하므로 여러 명이 동시에
  생성하면 대기 시간이 늘어난다. 고객 테스트 인원·시연 순서를 이에 맞춰 운영한다.

현재 `customer-validation@example.com`은 고객용 샘플 계정 하나다. 이번 작업에서 여러 참여자 계정을
임의로 추가하지 않았다. 이후 공개 회원가입은 초대 코드 없이 이메일·비밀번호로 직접 가입하도록 전환했다.
비밀번호·JWT를 Git이나 피드백 설문에 넣지 않는다. [공개 시연 보안 안내](PUBLIC_DEMO_SECURITY.md)를 참고한다.

## API와 저장 안정성

- `POST /api/v1/tryon-results`: 본인 의류 1~3개로 생성 요청 등록.
- `PUT /api/v1/tryon-results/{id}/image`: 최종 이미지 게시. 변경·삭제된 원본 사진으로는 게시할 수 없다.
- `GET /api/v1/tryon-results`, `GET /{id}`, `GET /{id}/image`: 본인 결과 조회.
- `DELETE /api/v1/tryon-results/{id}`: 본인 결과 삭제.
- `POST /api/v1/auth/activity`: 고객 세션 유효 시간 연장.
- `POST /api/v1/auth/logout`: 고객 세션 폐기.

영구 이미지 저장 전에 DB에 정리 의도를 커밋한다. 파일 저장이나 최종 커밋이 실패하면 정리 작업이
남아 재시도된다. 삭제는 DB에서 조회 불가로 만든 뒤 파일을 지운다. 파일 삭제에 실패해도 DB 작업이
남으므로 재시작 후 다시 정리된다. 탈퇴는 기존 계정 폴더 정리와 FK cascade를 사용한다.

마이그레이션 `0012`는 결과·파일 정리 테이블, `0013`은 계정 정책·세션 테이블을 추가한다.
기존 행과 의류 파일을 교체하지 않는다. `.env`는 읽거나 수정하지 않으며 검증은
`FITJANG_SKIP_DOTENV=1`과 명시적인 PostgreSQL 테스트 설정, 파일 접근 차단 감사 훅을 사용한다.

## 완료 검증

- 실제 PostgreSQL 격리 스키마 전체 테스트: 409개 통과, 2개 조건부 테스트 건너뜀.
  건너뛴 항목은 별도 팀원 체크아웃 및 지정된 실사 비전 이미지가 필요한 선택 검사다.
- 저장·커밋 실패, 파일 삭제 재시도, 다른 사용자 접근 차단, 동의 철회, 고객 로그아웃·미사용 만료,
  프로세스 메모리 소멸, 다른 프로세스의 세션 폐기, 업로드 임시 파일 비생성을 검증했다.
- 공개 HTTPS의 공용 DNS 릴레이를 통해 QA 하의·상의 및 고객 상의의 실제 로컬 GPU 생성을 확인했다.
  고객 전신 사진 DB 경로·착샷 행·사진 파일은 0건이고, 새 GPU outputs 파일도 0개다.
- 고객 로그아웃 후 기존 JWT는 401, 다른 계정의 결과는 404. 다시 로그인해도 옷장 9벌은 유지된다.
- 멘토 웹·백엔드 프로세스를 재시작하고 동일 결과의 SHA-256 일치 및 실제 화면의 576×864 이미지
  2장 로딩을 확인했다. PC 자체를 재부팅하지는 않았다.
- 기존 계정 6개·의류 42벌·추천 67건·코디 100건·피드백 7건 및 기존 이미지 63개를 유지했다.
  고객 정책 전환에 따른 사용자 행 갱신과 정상적인 요청 제한 카운터 갱신은 의도된 변경이다.
- 상세 검사 로그·비공개 보존 해시·화면은 Git에서 제외한 `.demo/tryon-persistence/`에 있다.
